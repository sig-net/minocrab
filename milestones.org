file and any =notes/= file it links. Findings and decisions get written to
=notes/= as they're made, so no session ever re-derives them. Mark tasks DONE
in place.

Closed milestones are kept in SUMMARY form: what they were, the headline
outcome, and where the full as-built record lives (the =notes/*.org= file
each names, plus git history). Open milestones are kept in full.

* M11 — Borsh (fixed-width subset) serialization
Design of record: =notes/borsh-format.org=. This IS Borsh, restricted
to the fixed-width subset and documented as A SUBSET, NOT A SEPARATE
FORMAT: every byte emitted is valid canonical Borsh for the declared
types, and any Borsh implementation (borsh-js included) parses it from
the same declarations. The subset rule is that every circuit-visible
type has a fixed width, so Maybe ↦ Flagged (bool tag + always-present
payload), never Option, and no Vec/String/data-enums. serde +
bincode-fixint emits byte-identical output for the subset, so spec
types derive both and conformance is a DUAL oracle.

      (byte-identical ZKIR) and the chip's digest IS keccak256(borsh(v)).

* M18 — Ergonomic parity for the optimized vault (dmd, 2026-08-16)
dmd's question, queued behind the ir-passes staging (notes/ir-passes.org §5
steps 3-5): "what optimisations would make the opt version of the erc-20
vault as ergonomic as the non-opt version?"
THE PREMISE NEEDS CORRECTING FIRST, and the correction is measured rather
than argued. The optimized vault is ALREADY the ergonomic one:
`erc20_vault_modern` is the SHORTEST of the four artifacts (1,608 lines vs
the port's 1,651) with zero raw `emit(` calls, and it is forked from borsh
which is forked from opt — every M10 optimisation is underneath it.
What the opt lineage actually costs is a PARALLEL VOCABULARY: it calls
`burn_spend` where the port calls `burn_coin`, `mint_shielded_token_to_key
_with` where the port calls `..._to_key`, `commitment_short`,
`assert_deployer_short`. The optimisation is encoded in the function NAME a
caller must know to reach for — the same shape as the `_under`/`_guarded`
halves staging step 3 retires. So the milestone's real question is which
suffixes can stop being lexical and become AMBIENT.
- [X] Design note first (the method every milestone since M14 has used):
      which of the opt vocabulary is a PROFILE and which is a genuinely
      different operation. First pass, to be checked rather than trusted:
      (a) `_with` (threaded `kernel.self()`) is MEMOIZATION, and its
      soundness paragraph is already written (M10 rung i: read count is
      framing, not protocol — every emitted read still reconciles through
      `process_read`). Under an opt profile `kernel::self_address` returns
      the cached read and every `_with` twin disappears. This is the typed
      CSE notes/ir-passes.org §3 says belongs in a gadget rather than a
      pass.
      (b) `commitment_short` / `assert_deployer_short` are a one-block hash
      shape — instruction selection from the type, which §4 keeps in the
      typed layer: the commitment builder picks the cheapest limbing.
      (c) `burn_spend` vs `burn_coin` is NOT ergonomics. Different protocol
      shape, different well-formedness warrant (tests/erc20_vault_opt_burn
      _wellformed.rs). Two names is right; the names should say what they do.
      (d) The M10 rungs that changed the SPEC (derived changeNonce,
      injective domain separator, Poseidon refund commitments) are not
      candidates at all — they are decisions, not spellings.
- [X] THE PRIZE, and the reason this is a milestone rather than a cleanup:
      if the choice is a profile rather than a spelling, `erc20_vault_opt`
      stops needing to be a separate SOURCE. The recurring cost in this
      repo is not that opt reads worse — it is that FOUR FORKS are edited
      in lockstep every time the API moves (M9 phase 7, M9 phase 8 and
      M17's `token_type` each paid it). Whether the fork can collapse
      depends on (d): a spec divergence cannot be a profile.
THE GOVERNING CONSTRAINT (dmd, 2026-08-16, on hearing the fork-collapse
idea): "correctness is the number one most important thing in this API."
So, stated before anyone reads the prize and reaches for the delete key:
- `erc20_vault` (the COMPAT port) may never collapse into anything. It is
  PI-equal to compactc and it IS the differential warrant — the whole chain
  `compactc ≡ port ≡ opt ≡ borsh ≡ modern` hangs off it. Collapsing it
  would not simplify the code, it would delete the evidence.
- A fork may only collapse where its divergence is LEXICAL. Item (d) above
  is the test: opt changed the spec in three places (derived changeNonce,
  injective domain separator, Poseidon refund commitments), and a spec
  divergence cannot be a profile. If those survive, opt stays a separate
  source and the honest answer to this milestone is "the vocabulary
  unifies, the fork does not".
- Every divergence ledger stays, asserted in BOTH directions. They are what
  makes a circuit leaving its predecessor's coverage an explicit edit; a
  collapse that removed a ledger would be trading a correctness instrument
  for line count, which is the wrong direction on this project's priority
  order.
Exit criteria: the opt artifact is written in the same vocabulary as the
port, with every remaining twin justified by a protocol or spec difference
rather than by cost — and the four-fork lockstep either gone or explicitly
priced. Not one instrument weaker than it is today.

* M24 — MinoCrab as a library: the GHC-API model (dmd, 2026-08-27)
The identity shift, dmd's: "this is primarily a library like the GHC API"
(https://hackage.haskell.org/package/ghc). GHC ships its innards as an
importable library so the whole Haskell tooling ecosystem — HLS, hlint,
plugins — is built WITHOUT forking GHC. MinoCrab should be the same for
ZKIR: expose the innards so third parties write their own super-optimised
ZKIR gadgets and their own optimisation passes ("compiler rules à la
carte") as ordinary crates, never a fork.
MinoCrab starts CLOSER to this than GHC ever was, because it is
library-first by construction — the eDSL IS the API — and the crate split
already mirrors GHC's internal layering: minocrab/minocrab-std are the
surface language + prelude, minocrab-ir is the "Core" layer (IR builder +
passes), minocrab-zkir is codegen/serialization, minocrab-sim is analysis
(cost model, region profiler, verification harness). The work is deciding
which seams become SUPPORTED extension points, not building the library
from scratch.
Motivated by the AA-manager port (2026-08-27, notes/manager-port.org),
whose −41%-rows-vs-compactc came entirely from the lowering levers this
milestone wants to hand to others.

DECISIONS OF RECORD (dmd, 2026-08-27):
- TIER THE SURFACE — a small semver-stable public API and an explicitly
  unstable internals tier, from day one (do NOT flatten everything, which
  is the GHC API's most-criticised trait — impossible to tell stable from
  incidental, breaks every release). KEEP THE STABLE API SMALL for now:
  "keep our hands free while we have very few users." Rust gives the tools
  Haskell lacked at the start (semver + module visibility + feature gates
  + a `minocrab-internals`-style crate or an `unstable` feature); draw the
  line up front rather than retrofit it (GHC's ghc-lib split came years
  in, painfully).
- SOUNDNESS DEFERRED, BUT DESIGN FOR IT. dmd: "I want to move over to
  having lean verification of steps later, I don't have the time for that
  right now, but build with the fact we're doing that later in mind." The
  path is already staged in notes/formal-verification-options.org
  (compile-fail tests → Kani → the Lean prover). CONCRETE DESIGN
  CONSEQUENCE: passes stay pure, total, `IR -> IR`, with the invariant a
  pass preserves STATABLE — no reaching into global mutable state, nothing
  a machine check (Kani now, per M23 R4; Lean eventually) could not
  target. Build the extension surface so the verification obligation can
  be BOLTED ON later without redesign; do not build the verifier now.
- NIX FLAKE CLI as a RELEASE-ONLY distribution pattern, not a dev
  dependency. dmd: "make sure we're not constantly rebuilding using nix,
  it's very slow"; "I don't mind if it stops working on main occasionally

THE METHOD (dmd, 2026-08-27) — a PER-CONSTRUCT loop, not a bulk port, and
the payoff lands in the TYPE SYSTEM rather than in a Lean file in a drawer:
  1. MAP — find our eDSL syntax construct's counterpart in Compact's
     syntax. The corpus ports already ARE this mapping in practice: each
     MinoCrab circuit is a Compact construct rendered in the eDSL.
  2. FIND — locate the Agda proof(s) about that Compact construct. Because
     the CHECKED Agda is STATIC/TYPING semantics, the constructs that have
     proofs are the source-level ones (well-formedness, typing rules) —
     which is precisely why this method fits the Agda we actually have,
     where a bulk port would not.
  3. PORT + CONSTRAIN — port the proof to Lean (machine-checked), AND
     reflect its invariants into MinoCrab's Rust TYPE SYSTEM so the types
     CONSTRAIN use of the feature to what the proof covers. The Lean
     proof is the WHY; the Rust type is the always-on enforcement at
     every call site. This is CLAUDE.md's "compile errors over panics"
     with a PROOF behind the constraint, landing on M24's type-level
     surface. A typing rule maps onto a trait bound / a distinct type that
     does not unify / an inline-const assert — the same ladder the hard
     rule already ranks.
     THE FIT (dmd, 2026-08-27): the Rust types are NOT required to cover
     EXACTLY the set of values the Lean proof allows. The requirement is
     SOUNDNESS in one direction — the types must admit a SUBSET of what the
     proof allows (never a value the proof does not cover) — and within
     that, the MAXIMAL such subset the type system can express at
     reasonable cost. Sometimes the subset is the whole set and the two
     coincide; often the proof's boundary is value-dependent or
     non-structural and the type-level approximation is properly smaller.
     Both are acceptable; admitting MORE than the proof is not.
     THE BALANCE: pick a reasonable point between usability and typing
     strength, leaning towards CORRECTNESS over usability but WITHOUT
     abandoning usability. A constraint that requires a type-level
     contortion no user could reasonably write (or read) is a worse
     product than a slightly smaller admitted set expressed plainly —
     and where tightening to the proof's edge would make the feature
     unspellable in practice, stop short and record the gap (the shortfall
     is an honest entry for the LIMITATIONS DISCUSSION below, not a
     failure of the loop).
  The deliverable of each turn of the loop is thus TWO things: a checked
  Lean proof, and a type-system invariant that makes only proven-safe
  usage spellable (the maximal usable subset, per THE FIT above).
