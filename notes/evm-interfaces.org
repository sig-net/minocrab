#+title: The EVM interface library (M38): ERC-20 and the interfaces beyond it

* 0. The ask (dmd, 2026-09-06)
"I want our library to have a generic ERC-20 constructor … what are the
most popular interfaces for contracts on Ethereum beyond ERC-20, and can
we define [them]?" and "put that in our vault contract and our examples".
Built on M37's =AbiType= / =EvmCall= / =Pending<Call, Env, WORDS>= layer
(notes/evm-calls.org §1–§3, as built §9–§11). This note is the design
of record for M38; the as-built sections follow per rung.

* 1. What M37 D left on the call type that is NOT a fact about the call
After rung D (evm-calls.org §11) =EvmCall= carries eight things. Six are
facts about the Solidity function and belong to a LIBRARY call type:
=NAME=, =Args=, =Return=, =Success= + =succeeded= (the rule by which the
return says it worked — an ERC-20 =transfer='s flag, a numeric return's
"executed is success"), =signature()= for the struct-argument shape, and
=GAS_LIMIT= (a per-function default; §2.3). Two are facts about ONE
DEPLOYMENT's protocol and are why D needed =Erc20TransferAsDeposit= and
=Erc20TransferAsWithdrawal= — the same Solidity function twice:
- =KIND= — the response kind byte. The vault files =transfer= under
  CLAIM (0) for a deposit and WITHDRAW (1) for a withdrawal; the
  treasury files its one =transfer= under 1 too (it reuses the WITHDRAW
  byte — a kind is per deployment, so a treasury may pick any). A library =erc20::Transfer=
  cannot own a kind.
- =RETURN_FIELD= — the deployed record's NAME for the attested return
  (=success=, =amountIn=, =shares=, =assets=; =None= → the anonymous
  =output=). A settle circuit's argument slot is named after it, so it
  is part of a deployment's interface, not of =transfer=.
Both move to the SLOT. That is rung A.

* 2. Design of record
** 2.1 The interface marker
#+begin_src rust
/// A callee interface: a set of functions an EVM contract claims to expose.
/// Sealed within the library's own set (Erc20, Erc4626, UniswapV3Router,
/// Weth, AaveV3Pool, Erc721, UsdtLike …); OPEN to contracts — a contract
/// declares its own callee marker in one line.
pub trait Interface: 'static {}

/// Inheritance. `I: Extends<Base>` says a `Contract<I>` may be handed a
/// `Base` call. Reflexive by the blanket impl; ERC-4626 IS an ERC-20:
/// `impl Extends<Erc20> for Erc4626 {}`. Weth IS an ERC-20 likewise.
pub trait Extends<Base: Interface>: Interface {}
impl<I: Interface> Extends<I> for I {}

pub trait EvmCall {
    type Callee: Interface;      // NEW — erc20::Transfer has Callee = Erc20
    …                            // NAME, Args, Return, Success, succeeded, signature, GAS_LIMIT stay
}

/// An address that CLAIMS interface `I` (was `Contract<Call>`).
pub struct Contract<I: Interface> { address: Bytes<20, Private>, … }
#+end_src
=request= / =request_with= take =callee: Contract<I>= with =I:
Extends<Call::Callee>=. A =transfer= filed against a
=Contract<UniswapV3Router>= is a missing trait impl (the ladder's first
rung); a =Contract<Erc4626>= takes both =erc4626::Deposit= and
=erc20::Approve= (an ERC-4626 vault is an ERC-20 share token).
CORRECTED at rung A (§4, adjustment 4): the vault does NOT exercise this
— =approve_stata= files =approve(stataToken, …)= ON =stata_underlying=,
the underlying ERC-20, with the stata token as the SPENDER argument; its
=Contract<Erc4626>= sites are =supply= / =redeem= with =erc4626::= calls
only. Inheritance is declared and tested (=evm_abi::
an_erc4626_vault_takes_an_erc20_call=) and its first shipped consumer is
rung B's =Weth: Extends<Erc20>=.
Coherence: =Extends= has a blanket reflexive impl, so a library
=impl Extends<Erc20> for Erc4626= is fine (distinct types), and a
downstream crate may write =impl Extends<Erc20> for MyToken= for its own
marker. It may NOT write =impl Extends<Erc20> for Erc4626= (orphan rule)
— the library decides its own inheritance, which is right.

** 2.2 The filing — where KIND and RETURN_FIELD go
DECISION: a =Filing= trait beside =EvmCall=, and a =Kinded<Call, KIND>=
wrapper as its off-the-shelf impl. NOT a fourth parameter on =Pending=.
#+begin_src rust
/// HOW ONE SLOT FILES ITS CALL: the call plus the two per-deployment facts.
pub trait Filing: 'static {
    type Call: EvmCall;
    /// The response kind byte this slot's records carry. A wire commitment
    /// (the MPC echoes it); distinct across a block (the Ledger derive's
    /// `assert_distinct_kinds` reads it from here, unchanged).
    const KIND: u8;
    /// The deployed record's name for the attested return; `None` is the
    /// anonymous `output`. Names a settle circuit's argument slot.
    const RETURN_FIELD: Option<&'static str> = None;
}

/// The one-line filing: this call at this kind, anonymous return.
pub struct Kinded<Call, const KIND: u8>(PhantomData<fn() -> Call>);
impl<Call: EvmCall, const KIND: u8> Filing for Kinded<Call, KIND> {
    type Call = Call;
    const KIND: u8 = KIND;
}

pub struct Pending<F: Filing, Env, const WORDS: usize> { … }   // was Pending<Call, Env, WORDS>
pub struct Succeeded<F: Filing> { … }                          // was Succeeded<Call>
pub struct Failed<F: Filing> { … }
#+end_src
WHY the wrapper and not =Pending<Call, Env, WORDS, KIND>=: the kind is
consumed by the TICKETS too (=complete= asserts =kind == KIND=, =refund=
selects the preimage by it), so a slot-parameter kind means
=Succeeded<Call, KIND>= on every settle signature, and WORDS is already
a number the author writes that the type should have inferred
(evm-calls.org §3). One name per slot, written once:
#+begin_src rust
/// The treasury.
type Transfer = Kinded<erc20::Transfer, 1>;
pub transfers: Pending<Transfer, Owned<Amount>, 2>,
pub fn complete(c, ticket: Succeeded<Transfer>) …
#+end_src
WHY =RETURN_FIELD= cannot ride on =Kinded=: a =&'static str= is not a
const-generic type on stable Rust. The vault, the one consumer that needs
the deployed names, writes four =Filing= impls of its own (three lines
each):
#+begin_src rust
pub struct Withdrawal;
impl Filing for Withdrawal {
    type Call = erc20::Transfer;
    const KIND: u8 = RESPONSE_KIND_WITHDRAW as u8;
    const RETURN_FIELD: Option<&'static str> = Some("success");
}
#+end_src
and =Erc20TransferAsDeposit= / =…AsWithdrawal= are deleted — they were
this trait spelled as two call types. Everything that read =Call::KIND=
/ =Call::RETURN_FIELD= in =evm_flow= reads =F::KIND= / =F::RETURN_FIELD=;
everything that read =Call::NAME= etc. reads =F::Call::…=. The record,
the notification and the dump do not change: the kind byte and the
field name are the same bytes from a different const.

** 2.3 What stays on the call, and why
- =GAS_LIMIT= — a per-function default (a =transfer= costs what a
  transfer costs). The vault's five values (=ERC20_CALL_GAS=,
  =SWAP_GAS=, =LENDING_GAS=) BECOME the library defaults, so re-homing
  is zero movement. A deployment that needs another limit uses
  =Envelope::caller= today; a =Filing::GAS_LIMIT= override with the
  call's as default is the cheap extension if a consumer asks
  (recorded, not done).
- =Success= / =succeeded= — the outcome rule is the function's (M37
  §3.2, D2/D4), not the deployment's.
- =signature()= — the struct-argument spelling is the function's.

* 3. Beyond rung A — pointers for B–G
- B: ERC-2612 =permit(owner, spender, value, deadline, v, r, s)= is seven
  static words (=Address, Address, U256, U256, U8, Bytes32, Bytes32=) —
  =U8= joins =AbiType= (the corpus has U24/U160 for the same reason).
  =UsdtLike= is a sibling INTERFACE whose =Transfer= / =Approve= have
  =Return = Unit= and =succeeded = always= — the §3.1 hazard in
  evm-calls.org is the reason it is a distinct marker: a USDT address
  handed to =Contract<Erc20>= would have its (absent) return read as a
  flag. =()= is not yet a =CircuitArg= (M37 finding iii), so a =Unit=
  ticket needs that first — B is where it lands or is recorded.
- C: Uniswap's =exactInputSingle= is the same nested-tuple =signature()=
  override as =ExactOutputSingle=; Aave v3 =supply(asset, amount,
  onBehalfOf, referralCode)= has a =uint16= (=U16=); =borrow= / =repay=
  carry =interestRateMode: uint256=.
- D: the alloy oracle — =alloy-sol-types= is what ~/mpc depends on; a
  test crate (or a dev-dependency of minocrab-contracts) declares each
  interface with =sol!= and asserts our selector and words against
  =SolCall::SELECTOR= / =abi_encode= on generated values. Not our
  encoder as its own witness.
- E: dynamic types are a WORDS problem — =Bytes<N>= is ceil(N/32)+2
  words at a fixed head offset, so the record stays static-width;
  =string= likewise; =T[]= with a length bound. Out until a consumer.
- G: the vault's four =Filing= impls (§2.2) and the treasury's
  =type Transfer = Kinded<erc20::Transfer, 1>= ARE rung G's "no
  contract-local call types remain" — landed by A, re-checked by G
  with the README side-by-side.

** Six places the design needed adjusting, and why
1. =Kinded='s impl needs =Call: EvmCall + 'static=, not just
   =Call: EvmCall=. =Filing: 'static= (§2.2) forces
   =Kinded<Call, KIND>: 'static=, which for
   =PhantomData<fn() -> Call>= means =Call: 'static=. Put on the IMPL
   rather than as a supertrait of =EvmCall=, so no existing call type's
   declaration changed.
2. =request_owned::<L>= COULD NOT TAKE =I= AS A NAMED PARAMETER. Rust
   has no partial turbofish: =request_owned::<OwnerCommitment>= with
   =<L, I>= is "method takes 2 generic arguments but 1 was supplied", so
   every call site would have had to spell the interface too. Fixed by
   taking the callee as ARGUMENT-POSITION =impl Trait= —
   =callee: Contract<impl Extends<Callee<F>>>= — which is an ANONYMOUS
   parameter and therefore not turbofishable, leaving =::<L>= naming
   exactly one thing. Done for =request= as well (same shape, a value
   callee). =request_with= keeps a named =I=: its callee is a CLOSURE
   returning =Contract<I>=, and =impl Trait= is not allowed in the return
   type of an =Fn= bound.
3. =Contract::from_address= NO LONGER INFERS ITS INTERFACE for an
   ERC-20 call, and every vault call site names it. With the reflexive
   blanket impl AND =impl Extends<Erc20> for Erc4626=, the bound
   =I: Extends<Erc20>= has TWO candidate impls, so =I= is ambiguous where
   nothing else pins it. That is not a defect: it is the type asking the
   author to say what the address claims, which is exactly the claim the
   callee-allow-list hazard is about. (=Extends<UniswapV3Router>= and
   =Extends<Erc4626>= have one candidate each and would infer; naming all
   seven keeps the lineage uniform.)
4. §2.1's INHERITANCE EXAMPLE IS A MIS-READING OF THE VAULT, and rung A
   does not exercise inheritance in a shipped circuit. §2.1 says
   "=approve_stata= approves an ERC-20 allowance ON the ERC-4626 vault".
   It does not: =approve_stata= files =approve(stataToken, 2^128-1)= ON
   =stata_underlying= — the callee is the UNDERLYING ERC-20 and the stata
   token is the SPENDER ARGUMENT, so the wrapper may pull the underlying
   during a supply. The vault's =Contract<Erc4626>= sites are =supply=
   and =redeem=, both filing =erc4626::= calls. So the vault has NO
   =erc20::= call on a =Contract<Erc4626>=, and the positive inheritance
   twin is a test rather than a lineage
   (=evm_abi::an_erc4626_vault_takes_an_erc20_call=, plus
   =the_interface_marker_costs_no_instruction=, which builds the same
   =approve= transaction through =Contract<Erc20>= and
   =Contract<Erc4626>= and asserts the ZKIR is equal). The inheritance
   itself is real and declared; it is waiting for a consumer.
5. THE GAS CONSTANTS MOVED THE OTHER WAY ROUND from what §2.3 implies.
   The library modules now DEFINE =erc20::CALL_GAS = 100_000=,
   =erc4626::CALL_GAS = 500_000=, =uniswap_v3::SWAP_GAS = 700_000=, and
   =erc20_vault='s =ERC20_CALL_GAS= / =LENDING_GAS= / =SWAP_GAS= are
   one-line aliases of them — a generic module must not import a
   deployment's constants. Same numbers, one definition;
   =evm::tests::the_gas_defaults_are_the_vaults= pins the equality, and
   the compat lineage's hand-written circuits keep spelling the names
   they always did. NOT MOVED: =FIXED_PRIORITY_FEE= / =FIXED_MAX_FEE=,
   which =evm::build_tx= still imports from =erc20_vault=. They are the
   fee ENVELOPE (a deployment policy, §2.3's own framing), not a
   per-function default. Recorded for dmd: either they follow the gas
   limits into the library as "the default envelope", or the envelope
   becomes wholly the caller's. Not decided here.
6. THE DUPLICATE-KIND MESSAGE WAS STALE. =assert_distinct_kinds= said
   "Give each =Response= type of the block a distinct =KIND=" — the
   =Response= types were retired in M37 D. It now says "Give each slot's
   =Filing= a distinct =KIND=". Message text only; the check is
   unchanged, and the ledger derive still emits
   =assert_distinct_kinds(&[<T as LedgerWidth>::KINDS, ..])= over the
   fields in declaration order (the derive's own test now asserts that
   list verbatim, not just that the call is present).

pub trait AbiType { const SOLIDITY; const RESPOND; type Wire<V: Vis3>; }   // the RETURN bound
pub trait AbiArg: AbiType { fn word<V: Vis3>(c, &Self::Wire<V>) -> B32<V>; } // the ARGUMENT bound

DECIDED: split the TRAIT, not the type. =AbiType= keeps the spelling and
the wire and IS the return position's bound; a new =AbiArg: AbiType=
carries =word= and is the argument position's. =AbiTuple='s element bound

** The payable design, and why that rung of the ladder
DECIDED: a marker trait =pub trait Payable: EvmCall {}= plus
=build_tx_payable= / =Pending::request_payable=, both bounded by it.
=weth::Deposit= is the only impl. Rejected alternatives, in the order the
brief offered them:
- =EvmCall::PAYABLE: bool= — a const cannot gate a method; the best it
  reaches is an inline-const assert inside the request, which is rung
  THREE of the ladder where rung one is available for the same work.
- =Envelope::with_value(Uint<128>)= — the fatal problem is not the
  spelling, it is that AN ENVELOPE DOES NOT KNOW ITS CALL. =Envelope= is
  built at the call site and handed to =request_with=, which pins the
  call afterwards, so a =with_value= on it cannot be bounded by anything
  about the call: a =with_value::<weth::Deposit>= turbofish would
  type-check and then be handed to a =transfer=. Making =Envelope=
  generic (=Envelope<C>=) would tie it, at the price of a type parameter
  on every existing signature and call site in the vault lineage — for no
  safety a bound on the REQUEST does not already give.
- A DISTINCT METHOD is what landed, because the request is the one place
  where the call, the callee and the amount are all in scope. It is also
  purely additive: no existing signature changed, so zero movement is a
  property of the diff rather than only a measurement.
Mechanically: =Tail::Named= gained =value: Option<Wire3<FieldT,
Private>>=, and =finish_tx= does =value.unwrap_or_else(|| c.constant(0))=
at exactly the point it used to emit the constant. =None= is every
non-payable call, so the immediate is named where it always was — which
is why the vault's seventeen and the treasury's three do not move.
=Envelope::ether= is PRIVATE; =build_tx_payable= is its only caller.
The converse is deliberately NOT enforced: a payable call may go through
the ordinary =request= (a =deposit= with no ether), which is what
Solidity means by payable.
rustc: =error[E0277]: the trait bound `erc20::Transfer: Payable` is not
satisfied= — a =compile_fail= doctest at BOTH layers (=build_tx_payable=
in =evm=, =request_payable= in =evm_flow=), each with the WETH twin.

=AbiLeafProbe= exists because the five SHIPPED calls between them never
pass a =bool= or a =bytes32= as an ARGUMENT (both appear only as returns),
so those two encoders would otherwise meet alloy nowhere. Its argument
tuple is all eight leaves — =(Address, Bool, Bytes32, U24, U64, U128,
U160, U256)= — at the maximum arity =AbiTuple= implements. It is also the
demonstration that a row is declarative: nothing in the harness knows it
exists.

Three assertions per row:
1. =Call::signature() == solCall::SIGNATURE=,
2. =Call::selector() == solCall::SELECTOR=,
3. the words our =AbiType::word= encoders build FROM CIRCUIT WIRES — run
   under =minocrab_sim::v3::simulate=, read back as bytes — equal
   =solCall { .. }.abi_encode()[4..]= split into 32-byte words.

(3) is the one that needed a harness. The values enter as circuit
arguments (=Circuit3::arg=), the wires are rebuilt from them, and
=AbiTuple::words= runs; the =B32= =(hi, lo)= pairs come back out through
=disclose= / =output=. =word_bytes= reassembles the thirty-two bytes and
then re-derives the slot pair with =vault::prims::b32_slots= and asserts
it matches, so a bug in the READER cannot hide a bug in the encoder.

NO DISAGREEMENT WAS FOUND. Every selector and every word agrees, at
=PROPTEST_CASES=5000= per row (0.89s for the file).

** How a row is added — three things, none of them harness code
1. A =sol!= declaration of the function as ETHEREUM spells it, in the
   interface's =sol_*= module. =uint256= wherever our word type is
   =U64=/=U128=/=U256=: those are OUR range bounds on a 32-byte word, not
   different Solidity types. A struct argument is a =struct= item plus a
   function taking it.
2. A =SampleLeaf= impl for any =AbiType= the call uses that has none yet —
   the host-side value, its proptest strategy, the field limbs it enters
   the circuit as, how to rebuild the wire. All eight of today's leaves
   have one; rung B's =U8= and rung C's =U16= are one impl each.
3. One row in the =oracle_rows!= table: a name, our call type, alloy's
   call type, and a closure-shaped pattern building alloy's struct from
   the destructured sample tuple.

=SampleLeaf: AbiType= and =SampleArgs: AbiTuple= are the only places the
oracle names the library's trait layer, deliberately: if rung B's
=AbiArg=/=AbiReturn= split renames =AbiType= in argument position, the
merge is a one-token rename in two supertrait bounds.

WHY A SEPARATE SAMPLE TRAIT rather than more methods on =AbiType=: the
sample side is test-only. The library's leaf trait says what a leaf IS on
the wire; how to generate a plausible value of one is the fixture's
business.

** The negative controls — three, because the oracle must be able to fail
1. =the_oracle_can_fail=: =transfer(address,uint128)= — the same name and
   arity with one type changed — must DISAGREE on the selector. It is also
   the argument for spelling =U64=/=U128= as =uint256= in every row: a
   =uintN= that was our RANGE rather than Ethereum's width would move the
   selector, and this is what that looks like.
2. =the_word_comparison_can_fail=: the selector control says nothing about
   the WORD loop (a harness comparing two empty lists would pass it). So
   =deposit='s two arguments TRANSPOSED must disagree, with the right
   order asserted EQUAL in the same test as the positive twin. Argument
   order is the right thing to perturb: it is invisible to the selector
   and it is exactly what an ORDERED =Args= tuple claims.
3. =the_router_shape_is_the_one_we_declare=: Uniswap's ORIGINAL
   =SwapRouter= has a =deadline= between =recipient= and =amountOut=; that
   eight-field struct is =db3e2198=, a different function our seven words
   would not fill. Ours is =SwapRouter02='s seven-field =5023b4df=. This
   is the control that matters for the one call whose =signature()= we
   override: =tests/evm_abi.rs= pins the extra PARENTHESES, this pins the
   FIELD LIST — and pointing a call type at the wrong router generation is
   a plausible mistake rather than a contrived one.

Plus two deterministic coverage tests that run even at
=PROPTEST_CASES=1=: =bool_covers_both_values= (both values, and the bool
word read off by hand) and =every_leaf_at_its_upper_bound= (each leaf at
the top of the range its Rust type claims).

** What could not be pinned, and why
- THE RETURN TYPES. =EvmCall::Return= is what the MPC attests and narrows
  (=AbiType::RESPOND='s =uint64= against =SOLIDITY='s =uint256=). The
  narrowing is a Signet protocol fact, not an ABI one, and alloy has
  nothing to say about it. =tests/evm_abi.rs= and =src/evm.rs='s unit
  tests keep those.
- THE TRANSACTION AROUND THE CALLDATA — nonce, fee envelope, gas limit,
  =to=. Not ABI; =tests/evm_abi.rs='s
  =build_tx_carries_the_declared_envelope= is where those live.
- =Unit=. It is a RETURN type with no ABI word, so there is nothing for
  alloy to encode; rung B is making a =Unit= in argument position a
  compile error, which is the right instrument for it.
- THE EMPTY ARGUMENT LIST (=()=). No shipped call has one, and =sol!= plus
  a zero-word row would assert only that =abi_encode()= is four bytes.
  Rung B's WETH =deposit()= / =withdraw(uint256)= is where a zero/one-word
  row becomes worth having.
- THE NAMES. alloy checks TYPES; a =sol!= parameter's NAME is not in the
  signature, so a row whose Solidity spells =receiver= where the deployed
  contract spells =to= would still pass. The interface's own EIP text is
  the only authority for those, and reviewing a row means reading it.
