#+title: Cases needing event/log attestation, not just receipt+return-data
dmd's ask (decisions.org B8): terse, concrete, verified cases where
receipt-status + return-data attestation isn't enough, for the MPC team.
Every claim below was checked against verified source (Etherscan/Blockscout,
address+file+function quoted) or a live =eth_call= on mainnet, 2026-09-06.

* 1. What the MPC attests today (sig-net/mpc @ =b940f0a7c6700dfbbf8e3a2a4af3aaffb052d354=)
=chain-signatures/chain-ethereum/src/execution_watcher.rs=,
=execution_confirmed_event= (L310-379): =receipt_succeeded = receipt.status()=
(L318); if false, =ExecutionOutcome::Failed= (L368-370), no other data
touched. If true, output comes from =debug_traceTransaction=, not the
receipt (=fetch_extraction_inputs=, L245-271) and is ABI-decoded against
the request's schema in =respond_bidirectional.rs=, =build_serialized_output=
(L123-161) via alloy =DynSolType::abi_decode= (=from_call_result=, L77-107,
decode at L88-90). A decode error is always =ExtractionFailure::Terminal=
(L300) -> =ExecutionOutcome::Failed= (L355-364) — indistinguishable from a
revert to anything reading the attested outcome.
- Schema expects =bool=, trace returns no bytes (=TraceOutput::NoReturnData=):
  =build_serialized_output= L147-149 hits
  =bail!("contract-call trace has no return data for non-empty output schema")=
  -> Terminal -> Failed. CONFIRMED.
- Schema expects =bool=, trace returns empty bytes (=TraceOutput::Output(vec![])=):
  falls to L140 =from_call_result=, alloy's =abi_decode= on an empty buffer
  for a 1-word tuple errors -> Terminal -> Failed. Same outcome, same path.
- Nothing in this file or =respond_bidirectional.rs= reads =receipt.logs=.
  =event_parsing.rs='s =logs=/=topic0= handling (grepped) is for the MPC's
  OWN =SignatureRequested=/=SignatureResponded= contract events, unrelated
  to the callee's logs. No log/event data is attested today, for any call.

* 3. Dropped (did not survive verification)
- *PAXG* =0x45804880De22913dAFE09f4980848ECE6EcbAf78=: proxy -> impl
  =0x7da4c5d9eCa180A03765a6d27196F2A0380fa543= -> imports
  =PaxosTokenV2.sol=. Its =_transfer= (L455-464) does a plain
  =balances[from]-=value; balances[to]+=value=, reverts on insufficient
  funds/frozen, NO fee code path exists. Not a fee-on-transfer token in its

- *ZRX* (considered as a "no-return token that fails silently" candidate,
  not in the original list): =0xE41d2489571d322189246DaFA5ebDe1F4699F498=,
  =transfer= (L60-67) DOES return =bool= and returns =false= without
  reverting on insufficient balance — but that's a real, decodable =bool=,
  i.e. exactly case 2 (already closed by =is_true=), not a new gap.
  Mentioned only because the search for "no-return AND silent-fail" (BNB,
  OMG) came up empty and this was the closest near-miss.
- Aave v3 =Pool.supply()= (=0x87870Bca3F3fD6335C3F4ce8392D69350B4fA4E2=
  proxy, impl =0x728a138A4823392C2EFA55e028d434F526fE03CF=,
  =SupplyLogic.executeSupply=, L40-89): void return confirmed, but checked
  the mint math — =IAToken.mint= is called with =scaledAmount= computed
  from =params.amount= (the caller's declared amount), NOT the actual
  =safeTransferFrom= delta (L62-67). So "mined without reverting" IS
  sufficient — PROVIDED the reserve isn't a fee-on-transfer token, which is
  a governance/listing invariant Aave enforces off-chain, not something
  this function checks. Not dropped as a candidate, but confirmed as
  *not currently a gap* — matches evm-interfaces.org \S6 open question 4's
  own conclusion; recorded here as verified rather than asserted.

* 4. Could not verify
- Whether the MPC's respond/output schema format (the JSON =[{name,type}]=
  list feeding =parse_output_schema_fields=) can express a dynamic
  array-of-tuples (=Result[]= for Multicall3's =aggregate3=). This needs
  reading the schema parser and whatever consumes =respond_serialization_schema=
  on the signing side, which is out of scope here. If it can't, aggregate3
  degrades to the same "mined without reverting" problem as the void-return
  cases despite having a fully informative return type in principle.

* 5. What the attestation would need to carry (options, not a decision)
For the void-return and misleading-return cases above, the fix is some form
of log attestation layered on the existing receipt+return-data path: (a)
the MPC decodes a caller-declared =(address, topic0, ABI type)= against the
matching log(s) in the receipt exactly the way it decodes return data today
— reuses the existing schema/Terminal-failure machinery, just points it at
=receipt.logs= instead of the trace output, and is the smallest change; (b)
the MPC attests raw filtered logs (address+topic0 match, full data) and lets
the requester's own circuit decode/interpret them, trading MPC-side schema
work for more data crossing the wire; (c) a receipt-logs inclusion proof
(Merkle proof against the block's receipts root) that lets the destination
verify a specific log was actually emitted without the MPC being a trust
point for the decode at all, at the cost of proof size/verification work on
our side. All three still need the MPC to fetch and expose =receipt.logs=,
which today (\S1) it does not do anywhere in this path.
