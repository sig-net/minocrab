The milestone's first bullet (milestones.org M27, "DESIGN NOTE FIRST"):
the instruction inventory with operand/output arity, the consumption

* 0. Ground, restated in one paragraph

The thing being given a semantics is the ARTIFACT: a =.zkir= v3 file as
compactc writes it and as =zkir-v3= / the proof server read it. Its
de-facto spec is Rust (notes/zkir.org "Where ZKIR is defined"): the
=Instruction= enum with per-variant doc comments in
=zkir-v3/src/ir.rs= (rev 04c9c5d9, the rev Cargo.toml pins and the
bundled binary is built from), and the two walks in
=zkir-v3/src/ir_vm.rs= — =preprocess= (off-circuit, lines 185-691) and
=circuit= (in-circuit, lines 705-1210). No Agda, no prose spec, nothing
upstream says anything formal about it (lean-port.org §0). Our own
readers are re-exports (=minocrab-zkir/src/v3.rs=: =IrSource::load=
plus the version-envelope rewrite), so the Lean is not modelling our
code — it is modelling THEIRS, and the corpus is the instrument that
keeps the model honest (M27 decision: corpus-gated forever).

* 1. The wire format, exactly (rung 1's target)

** 1.1 Envelope
=IrSource= (ir.rs:59-72): =version= (minor, serde =u8=; on disk wrapped
as ={"major": 3, "minor": 0}= — =IrSource::load= rewrites inward,
=minocrab_zkir::v3::to_disk_form= outward), =inputs : Vec<TypedIdentifier>=
(={"name", "type"}=), =outputs : Vec<IrType>=, =do_communications_commitment
: bool=, =instructions=. The only minor that exists is 0
(=IrMinorVersion::V0=, =#[non_exhaustive]=; =load= accepts =3.0..=0=
only). Corpus: 84/84 files are 3.0.

** 1.2 Lexemes
- Identifier: a string starting with =%= (ir.rs:258-265 rejects
  anything else); compactc mints =%<sym>.<counter>= (print-zkir-v3.ss
  =var->string=). The Lean type is just =String=; the =%= rule is a
  parse-time check, not a structural invariant (the Rust type is
  =Identifier(pub String)= too).
- Immediate: ="0x"= + lowercase hex, LITTLE-ENDIAN BYTES of the
  integer, minimal length with at least one byte (=0x00= is zero), and
  an optional leading =-= (print-zkir-v3.ss =zkir-field-rep->string=:
  compactc holds a signed Scheme integer and prints =-0x…= for
  negatives). Corpus: 10,476 immediates, all even-length, all
  lowercase, no =0X=; 36 files carry negatives, all of them =-0x01= or
  =-0x02=; the widest is 31 bytes (66 chars) — every corpus immediate
  has |v| < 2^248 < p. The Rust reader maps both forms to one =Fr=
  (ir.rs:225-267: =Fr::from_le_bytes= then negate), and the Rust
  WRITER never emits a minus (ir.rs:210-223 prints the reduced
  element's bytes). THEREFORE: byte-exactness forces the syntax tree
  to keep the SIGNED LITERAL (=Int=), and the semantics maps it into
  the field (§4). Two syntax trees (=-0x01= and =0x<p−1 as bytes>=)
  denote one field element; that is a property of the semantics, not
  a parser ambiguity. Rung-1 lemma to state: every corpus immediate is
  in (−p, p) (so the mapping is the obvious one, no reduction hidden).
- Operand = Identifier | Immediate, distinguished by the first char
  (ir.rs:232-266).
- Types: the 13 =IrType= names, serde-renamed (ir_types.rs:36-88):
  =Scalar<BLS12-381>=, =Bytes<32>=, =Point<Jubjub>=, =Scalar<Jubjub>=,
  =Point<Secp256k1>=, =Base<Secp256k1>=, =Scalar<Secp256k1>=,
  =Point<Secp256r1>=, =Base<Secp256r1>=, =Scalar<Secp256r1>=,
  =Point<Curve25519>=, =Base<Curve25519>=, =Scalar<Curve25519>=. Corpus
  uses three: =Scalar<BLS12-381>= (1141 sites), =Point<Secp256k1>=
  (12), =Scalar<Secp256k1>= (41). The inductive carries all 13; the
  printer is total over them; only three are corpus-exercised (say so
  in the gate output).
- Alignment (FAB, =base_crypto::fab::Alignment=): a vector of segments;
  compactc emits only ={"tag": "atom", "value": {…}}= with atom values
  ={"length": n, "tag": "bytes"}=, ={"tag": "field"}=, ={"tag":
  "compress"}= (print-zkir-v3.ss =alignment-atom->alist=; NOTE the key
  order =length= BEFORE =tag= inside a bytes atom). =Option= segments
  exist in the Rust type but compactc never prints them and the
  in-circuit decoder rejects them (ir_vm.rs:114-119). Corpus: 666 atoms,
  ALL =bytes=; no =field=, no =compress=, no option. The Lean inductive
  carries =bytes n | field | compress= plus an =option= segment
  constructor only if rung 1 needs it to PARSE — it does not (corpus),
  so: OMIT it and let the parser reject it, recorded as a deliberate
  SUBSET of the Rust type (a file using it cannot synthesize anyway).

** 1.3 Layout — compactc's =print-json-compact= (json.ss:399-472)
Byte-exactness is against THIS printer, not serde's. It is a 40-line
depth-driven function, transcribable verbatim into Lean:
- objects: ={= then each pair; at depth ≤ 1 (the top object) pairs go
  on their own line indented 2·depth, else inline with one leading
  space; ="key": value=; pairs comma-separated; close =}= on its own
  line at the top, else preceded by one space.
- vectors: =[= then elements; at depth ≤ 2 each element starts on a
  new indented line (this is why every instruction and every input is
  one 4-space-indented line, and why a non-empty =outputs= list prints
  one type per line); deeper vectors are inline with a single space
  after each comma and NO space inside the brackets (=["0x30"]=,
  =[{ "tag": "atom", … }, { … }]=). Close =]= on its own line when the
  vector's own depth ≤ 1 — hence the empty-outputs shape =[\n  ]=.
- strings escaped per lines 402-420 (none of the escapes occur in the
  corpus; the Lean printer implements them anyway, they are six cases).
- integers =~d=; booleans; =null= for the absent guard (compactc prints
  =(void)= — "warty", their comment, print-zkir-v3.ss:141).
- a trailing newline after the top object.
Instruction objects follow compactc's KEY ORDER PER OP (print-zkir-v3.ss
=Instruction=), which is NOT the Rust enum's field order (e.g.
=cond_select= prints =output, bit, a, b=; =public_input= prints =type,
output, guard=). The per-op order table is part of the printer, cited
line by line. The Rust reader is order-insensitive (serde), so this is
invisible to Rust and load-bearing only for us.

* 3. Consumption rules already decoded (nothing new here; collected)

** 3.1 The four streams and their cursors
A =ProofPreimage= (transient-crypto/src/proofs.rs:716-732) carries
=inputs=, =private_transcript=, =public_transcript_inputs=,
=public_transcript_outputs=, =binding_input=,
=communications_commitment : Option<(Fr, Fr)>=. Consumers, from §2:
=inputs= → prologue only; =private_transcript= → =private_input=
(guard-true), width =encoded_len(type)=; =public_transcript_outputs= →
=public_input= (guard-true), same width; =public_transcript_inputs= →
=impact= (guard-true), one element per operand, checked for equality
as consumed. A false guard consumes NOTHING from its stream but still
contributes zeros to =pis= (impact) or a default value (inputs). The
OBSERVABLE PI STREAM is therefore a deterministic function of the
instruction list and the guard values: =pis = [binding, comm?] ++
concat(for each impact: guard ? inputs : zeros)=.

** 3.2 FAB alignment ↔ operand mapping (taint.rs:337-416 =audit_hash=,
transcribed from ir_vm.rs:125-180 =fab_decode_to_bytes_atom=)
Per alignment segment, in order: =field= atom consumes ONE operand
(31-byte-capable field element, whole value); =bytes{length}= consumes
=ceil(length/31)= operands: if =length mod 31 ≠ 0= the FIRST operand
is the stray limb of width =length mod 31=, then =length div 31=
full 31-byte limbs — and IN-CIRCUIT the full limbs are read in REVERSED
operand order (=inputs[chunks-1-i]=, 167) while the stray limb's bytes
are appended AFTER them (170); =compress= and =option= are rejected.
Leftover operands = malformed. Off-circuit the same value is built by
=alignment.parse_field_repr(&inputs)= then =binary_repr= (493-498);
the two must agree on the byte string — the ONE place where rung 3's
"uninterpreted hash" needs a concrete PRE-function (operands → bytes)
so that the inventory can say WHICH operands a digest binds. The
byte-string builder is therefore CONCRETE at rung 3 (it is bit
manipulation, no crypto); only SHA-256/Keccak are uninterpreted.
The lint's limb-width bound (=bits(m) ≤ 8·w=) rides on this same
mapping (M23 R3) — cite, do not rebuild.

** 3.3 Typed value encoding
=encode_offcircuit= / =decode_offcircuit= (ir_instructions/encode.rs)
turn an =IrValue= into =encoded_len= Natives and back: Native ↦ itself;
Bytes32 ↦ (low 31 bytes as LE Native, high byte) — the same split as
=bytes32_into_low_high=; foreign elements ↦ two limbs; points ↦
coordinate limbs (+ identity flag on Weierstrass). Rung 3 needs
Native/Bytes32 concrete (they are the corpus) and the foreign cases as
uninterpreted =encode_T / decode_T= with the arity fixed.

* 4. The two semantic readings, and who needs which

** 4.1 EVALUATION (the =preprocess= reading) — rung 3's primary
A total function
  =run : Program → Preimage → Except Reject Result=
where =Result = { memory, pis : List Fr, pi_skips : List (Option Nat),
outputs : List Value }=, defined by folding =step= over the instruction
list with state =(memory, pis, pi_skips, cursors × 3, outputs)= exactly
as §2's column, then the epilogue checks. Immediates are =Int= in the
syntax and are mapped to =Fr= at =resolve_operand= (ir_vm.rs:235-239:
an immediate always resolves as =Native=). Observables (the milestone's
"PI/witness/output streams"): =pis=, =pi_skips=, =outputs=, the
accept/reject bit, and — for the inventory — the CONSUMED PREFIXES of
the three transcripts (which is what "the witness inventory per
circuit" means mechanically: the private_input instructions on the
taken guard path, with their types).

** 4.2 CONSTRAINT (the =circuit= reading) — stated beside it
The solution set: for a program and a fixed PI vector, the set of
memory assignments (one value per defined identifier, of its type)
that satisfy every constraint the in-circuit arm lays down. Stated as a
predicate =Sat : Program → PIs → Assignment → Prop= over the same
inductive, one clause per constraint-bearing instruction (§2 rows
"constraint", "compute+constraint", the =convert=-to-bit sites, the
public-input equalities, and the epilogue's commitment equality).
Compute instructions become functional equations (=mem[output] =
f(mem[operands])=); intrinsics appear as the same uninterpreted symbols
as in 4.1 (one =Model= record, §5, shared by both readings — that
sharing is what makes the completeness lemma statable).
COMPLETENESS LEMMA (rung 3 gate item): honest evaluation satisfies the
constraints — =run P π = ok r → Sat P r.pis r.memory= — proved per
instruction for the ones that carry both readings. Not soundness
(constraints ⇒ evaluation): that direction is exactly the UB/divergence
list in 4.3 and is NOT claimed.

** 4.3 Where the two walks are known to differ (recorded, not hidden)
- =assert=: off-circuit requires cond ∈ {0,1} and =1; in-circuit
  =assert_non_zero= — a cond of 2 is rejected by =check= but satisfiable
  in-circuit (ir.rs:415 "UB").
- =less_than=: off-circuit rejects operands ≥ 2^bits; in-circuit
  compares at width =max(bits + bits mod 2, 4)= with UB beyond
  (ir.rs:863-865, ir_vm.rs:960-966).
- =public_input= / =private_input= guards are NOT constrained in-circuit
  (ir.rs:894): a guarded-off input is a free witness in the constraint
  reading and a typed default in the evaluation reading.
- =bytes32_into_low_high=: no constraint at all in-circuit (ir.rs:651).
- =cond_select=, =not=, =impact= guards: in-circuit the =convert= to
  =AssignedBit= constrains booleanness; off-circuit a non-boolean is a
  reject. (Agree on the 0/1 domain; differ on what happens outside it.)
These are facts about upstream's design, useful to the honest-boundary
writeup; none is a finding to report (they are documented UB).

* 5. The intrinsic-function boundary (rung 3 uninterpreted, rung 4 concrete)

Value domain at rung 3:
  =Value = native (Fr) | bytes32 (Vector UInt8 32) | jubjubPoint (J) |
  jubjubScalar (Js) | k256Point | k256Base | k256Scalar | p256… |
  c25519…=
with =Fr := Fin p= (p the BLS12-381 scalar modulus, a literal) — the
milestone says =ZMod p=; in Mathlib =ZMod p= for =p > 0= IS =Fin p= by
definition, and the two Lean packages already in the repo are
mathlib-free by decision (lean-port.org §5: "plain Lean 4 so the check
loop is seconds"). =Fin p= gives =+ * -= modulo p from core; =inv= is
defined by exponentiation to =p − 2= (total, =inv 0 = 0=, matching the
off-circuit =bail= only through the =Except= wrapper). Bytes32 is
concrete. The foreign carriers are OPAQUE types at rung 3: fields of a
=Model= structure, with the intrinsics as further fields:
  =transientHash : List Fr → Fr=, =sha256, keccak256 : List UInt8 →
  Vector UInt8 32=, =hashToCurve : List Fr → J=, =ecMul= per curve,
  =ecMulGen= (Jubjub, k256), =intoCoords / fromCoords= per curve,
  =intoBytes32_T / fromBytes32_T= for the six foreign fields,
  =jubjubScalarFromNative=, =encode_T / decode_T= for the foreign
  types, =transientCommit : List Fr → Fr → Fr=, plus the foreign
  =add/mul/neg/inv/eq/select=.
Everything Native/Bytes32 is concrete at rung 3 already: =add mul neg
inv=, =test_eq=, =cond_select=, =not=, =less_than= (Nat comparison of
=Fin= values under the bit checks), =div_mod_power_of_two=
(=val / 2^bits=, =val % 2^bits= on the Nat), =reconstitute_field=,
=into/from_bytes32= on Native (LE bytes of the canonical Nat; the
=from= direction reduces mod p), =reverse_bytes=, the low/high pair,
and 3.2's FAB byte builder. So rung 3 is a REAL interpreter for every
corpus circuit that uses no curve op and no hash — and, with the
hashes uninterpreted, the inventory's "component c = H(these
operands)" statements are exactly what rung 3 proves.
Rung 4 instantiates the =Model=: SHA-256 and Keccak-256 ported
mechanically (pure byte algorithms, LLM-writable, differential-
validated against the Rust digests on the corpus preimages); Poseidon
(=transient_hash=, midnight's parameters) ported mechanically from
transient-crypto; Jubjub arithmetic (twisted Edwards over =Fin p=)
likewise; the secp256k1/r1/curve25519 ops ONLY if a corpus preimage
exercises them (12 + 41 type sites, all in the signet-integration
ECDSA circuits) — otherwise left uninterpreted at rung 4 too, said so.
That is the variance rung and the milestone's estimate driver; its
shelve-point is explicitly fine.

* 6. The rung-4 differential interface (preimage dumps)

What exists: =MINOCRAB_DUMP_PREIMAGES=<dir>= makes the differential

* 8. The Lean package: where, what, gates

WHERE: a third lake package at =crates/minocrab-zkir/lean/=
(=MinocrabZkir=), beside the reader it models — L0 is where the wire
format lives (architecture.org), the two existing packages sit beside
the crates whose code they warrant, and the crate SHIPS =lean/= like
the others (Cargo.toml =include=, =.lake/= gitignored). Mathlib-free
(§5). =import Lean.Data.Json= (core, not Mathlib) for the parse side:
the gate is on the PRINTER (=print (decode (Json.parse s)) = s=), so a
lenient generic parser is fine and reusing core's is the
reuse-before-writing rule applied.
MODULES: =Syntax.lean= (the inductive: =IrType=, =Operand=, =Segment=,
=Instr= — 33 constructors — =Program=), =Print.lean= (json.ss's layout
+ print-zkir-v3.ss's key orders, both cited), =Parse.lean= (Json →
Syntax), =Dataflow.lean= (=reads=, =defines=, =guardOf=,
=impactPushes=; exhaustive by =match=), =Semantics.lean= (§4.1 =run=,
§4.2 =Sat=, the =Model= record), =Passes.lean= (the eight theorems over
