#+title: Supply-chain CI: cargo-deny (M38 D2)

notes/decisions.org D2, from notes/evm-interfaces.org §7: M38 D added the
first sizeable crates.io graph (alloy, ~20 dev-only transitive crates) and
CI had no supply-chain job. This adds one: =deny.toml= at the workspace
root, a =deny:= job in =.github/workflows/ci.yml=, and =pkgs.cargo-deny= in
=flake.nix='s devshell (nixpkgs has it; one package line, same posture as
=cargo-semver-checks=).

* What the job runs
=nix develop -c cargo deny check= — all four of cargo-deny's default
checks (advisories, bans, licenses, sources) against =deny.toml=. Same
command locally and in CI (the =deny:= job, pull_request + push like every
other gate).

* =[graph] targets=
Restricted to the tree's actual footprint: =x86_64-unknown-linux-gnu= and
=aarch64-unknown-linux-gnu= (CI's =ubuntu-latest= runner, and Linux dev
boxes) plus =x86_64-apple-darwin= / =aarch64-apple-darwin= (flake.nix's
=compactcTarget= map — where dmd develops). Left unrestricted, cargo-deny's
default graph walk includes every target Rust knows about, which pulls in
Windows- and UEFI-only crates (=windows-*=, =jni=, =r-efi=, …) that never
build here and inflate both the license list and the duplicate-version
count with things that aren't really in the tree. Two license entries
(=BSD-1-Clause= from =fiat-crypto=, =CDLA-Permissive-2.0= from
=webpki-root-certs=) disappeared entirely once restricted — genuinely not
present on any target we build for — and were dropped from the allow list
rather than kept "just in case".

* Licenses — the allow list is the actual set present
=cargo deny list= (restricted to the targets above) is the source of
truth; nothing was added speculatively. Allowed:
=0BSD=, =Apache-2.0=, =Apache-2.0 WITH LLVM-exception=, =BSD-2-Clause=,
=BSD-3-Clause=, =CC0-1.0=, =ISC=, =MIT=, =MIT-0=, =Unicode-3.0=,
=Unlicense=, =Zlib=. All permissive; no copyleft license is actually
allowed by this list.

One SPDX expression worth naming even though it needed no allow-list
change: =r-efi= (a UEFI-target-only crate, invisible under our restricted
targets, so it isn't even in the graph above) is triple-licensed =MIT OR
Apache-2.0 OR LGPL-2.1-or-later= upstream — cargo-deny's =list= command
buckets a crate under every disjunct of its SPDX expression, which is why
an unrestricted run shows "LGPL-2.1-or-later" at all. It is satisfied via
its MIT/Apache-2.0 alternative wherever it *is* on a target's graph, and
LGPL-2.1-or-later is deliberately NOT on the allow list — if some future
target pulls in a crate whose *only* license is copyleft, the check must
fail, not silently pass because =r-efi= already normalized the string.

=[licenses.private] ignore = true=: our own workspace crates (path/git
members, none published yet) and the two interface crates are skipped —
they already declare =license = "MIT OR Apache-2.0"= via
=[workspace.package]=, nothing to check.

Two crates ship without a machine-readable license expression at all
(=no-license-field=, warning severity — does not fail the check):
=midnight-circuits= (both 6.3.0 and 7.2.4) and =midnight-zk-stdlib= (both
1.2.1 and 2.3.3), both plain crates.io dependencies pulled in by the
pinned =midnight-*= git crates. Not clarified via =[[licenses.clarify]]=
(would need fetching each crate's =LICENSE= file and hashing it) — logged
here instead since it doesn't block the gate; revisit if cargo-deny ever
makes =no-license-field= deny-by-default.

* Sources — allowed by exact URL, not by org or wildcard
=unknown-registry= and =unknown-git= are both =deny= (stricter than
cargo-deny's own default of =warn=): this job exists specifically to
catch a dependency from a host nobody chose, so an unrecognized source
should fail the build, not just print a note.
- =allow-registry = ["https://github.com/rust-lang/crates.io-index"]=
  (the default, spelled out).
- =allow-git = ["https://github.com/midnightntwrk/midnight-ledger"]= — the
  one git host the tree depends on, matching every =git = "..."= line in
  Cargo.toml's =[workspace.dependencies]= (the pinned =midnight-*= crates,
  all at rev =04c9c5d9bcebb8d4427d8589fb54d58a55599c14=) and the
  =[patch.crates-io]= block (=midnight-transient-crypto= at tag
  =transient-crypto-2.2.0-rc.1=, =midnight-serialize= /
  =midnight-base-crypto= at the same rev) — by URL, no
  =[sources.allow-org]= entry, so a second midnightntwrk repo would still
  need adding by hand.

* Bans — duplicate versions reported, not gated
=multiple-versions = "warn"=: the tree already carries duplicate versions
of crates it doesn't control the resolution of (two generations of
=midnight-curves=/=midnight-transient-crypto=/=midnight-zk-stdlib= living
side by side — the v2/v3 zkir split notes/midnight-code-reuse.org already
documents — plus the usual proc-macro-graph churn: four =syn= majors,
two =quote=, two =rand=/=rand_core=, etc). None of these are a
supply-chain risk by themselves; failing the build on them would be
noise, not signal. A run against the restricted targets above found
*27 crates* with duplicate versions (28 extra lock entries — =syn= alone
carries four: 0.11, 1.0, 2.0 and 3.0). Ratchet to =deny= plus
=skip=/=skip-tree= entries if that count starts climbing without reason.

* Advisories — every ignore, with its reason
Two RUSTSEC IDs and one yanked-version notice, all found on a clean run
and all pulled in transitively — nothing the tree depends on directly
picked either RUSTSEC-flagged crate:

- =RUSTSEC-2025-0141= (bincode 2.0.1, "unmaintained" — the bincode team
  disbanded after a harassment incident, not a vulnerability). Reaches
  the tree two ways: transitively via the pinned midnight-ledger rev
  (=midnight-zk-stdlib= → =midnight-transient-crypto= → …), AND as our
  own dev-only =bincode = { version = "2", ... }= workspace dependency
  (Cargo.toml: the second conformance oracle for the borsh format,
  notes/borsh-format.org) — pinned to the exact 2.0.1 midnight's own lock
  already resolves, so there is no independent version to bump to. No
  safe upgrade exists upstream (bincode 1.3.3 is the team's own
  recommended "complete" version, but that's a downgrade, not a fix).
- =RUSTSEC-2024-0436= (paste 1.0.15, "unmaintained" — repository archived
  by its author, not a vulnerability). Transitive via alloy/midnight-curves'
  proc-macro graph (M38 D's alloy oracle, dev-only). Not a direct
  dependency; nothing to repin.
- =chacha20@0.10.1= (yanked version notice, not a RUSTSEC ID). Transitive
  via =rand 0.10.2= → =atomic-write-file= → =midnight-base-crypto=, i.e.
  the pinned midnight-ledger rev again. Recorded explicitly rather than
  left to the default warn-and-continue, per the instruction to never let
  a firing advisory pass silently.

All three are in =deny.toml='s =[advisories.ignore]= with a reason
string each (cargo-deny still prints a note when an ignored entry is
encountered — nothing here is silent). None is a live vulnerability;
each is either "the maintainer stopped" or "the version was pulled",
and in every case the crate in question arrived through the pinned
midnight-ledger rev, not a choice this tree made. Revisit when
midnight-ledger's own dependency graph moves off any of the three.

* Gate result (2026-09-06, restricted targets)
: advisories ok, bans ok, licenses ok, sources ok
No vulnerability (as opposed to unmaintained/yanked) advisory has ever
