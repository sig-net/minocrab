#+title: IR passes — but only the ones that buy API

Design of record for the pass work dmd asked for (2026-08-16): *"look at any
optimisation pass (ours or theirs) that can make our API more ergonomic and
composable"*, with the standing criterion from the same conversation —
**only do this if it makes us able to write simpler code, higher up the
stack, which then optimises in a composable way.**

So rows are NOT the objective here. Rows are the constraint: a pass has to
not cost any, and where it happens to save some that is a bonus rather than
the case for it.

* 0. THE MEASUREMENT, first, because it decides most of the argument

"Are we duplicating ZKIR's work?" is not guessable and was not guessed. It
is measured in [[file:../crates/minocrab-contracts/tests/backend_folding.rs][tests/backend_folding.rs]], against Midnight's own cost model
— the same one =row_snapshot= and the benchmark harness use — and committed
so a toolchain bump breaks it rather than silently invalidating this note.

| pattern | rows each | backend folds it? |
|---------+-----------+-------------------|
| =copy= of an immediate | *0* | YES |
| linear op with a constant operand (=add x, 0=) | *0* | YES |
| unused pure instruction | 1 | no |
| duplicated pure instruction | 1 | no |
| repeated =constrain_bits= on the same wire | *2* | no |

Three consequences, and they are most of the design:

** (a) Constant folding above ZKIR buys ZERO rows

Every contortion we have made to avoid emitting a =copy= of an immediate —
M9 phase 7's operand positions, M9 phase 8's inlined guard, M16's
=AnyWire3::immediate=, M17's =UnshieldedToken= — bought DIFFERENTIAL
FIDELITY with compactc. Not cost. Nobody wrote that down at the time, and
the fifth one (changing =LedgerRepr=, which dmd approved on 2026-08-16) was
about to be paid for the same unstated reason.

That does not make the pass worthless. It relocates the case for it: it is
worth building because it lets us DELETE those five special cases, not
because it makes anything faster. Which is exactly dmd's criterion.

** (b) The costliest redundancy is the one that would buy the most safety

A repeated range constraint costs TWO rows — twice a multiply, and more than
any other redundancy measured. That is why the Borsh layer's docs say
"PRECONDITION: the value's leaves are already range-constrained" instead of
just constraining them, and why =Uint::widen= has a paragraph explaining
that it deliberately does not re-constrain.

Those are load-bearing comments standing in for a check, which is the least
composable thing in the codebase: a gadget cannot defend itself, so every
caller has to be right. A deduplicating pass turns that into "constrain
whatever you like, the pass removes what is provably redundant" — safer
code, simpler contracts, and it removes rows rather than adding them.

** (c) Dead code and common subexpressions are real rows, and still not ours

Neither is folded, so both leave rows on the table. Both are nonetheless
rejected below, for reasons that are about correctness rather than value.

* 1. THE CONSTRAINT NOBODY SHOULD FORGET

Our primary correctness warrant is DIFFERENTIAL EQUALITY with compactc —
instruction for instruction, for the M14/M15/M16/M17 fixtures. A pass that
makes us *match* compactc more closely is free. A pass that makes us *beat*
compactc costs us that test, and we know the price because M10 paid it: the
optimised vault proves its own preimage and its warrant is symbolic-effect
equivalence plus a nine-million-case harness instead of PI-equality.

So passes divide cleanly:

| pass | vs compactc | gate |
|------+-------------+------|
| constant folding | DIVERGES by inlining (see §8) | always on, both sides normalised |
| guard scoping | neutral (same stream) | always on |
| constraint dedup | DIVERGES | opt profile, M10 warrant |
| dead code elimination | diverges | rejected, see §3 |
| common subexpression elimination | diverges | rejected, see §3 |

* 2. THE THREE TO BUILD

** (i) Guard scoping — the biggest API win, and not the backend's job

Every ledger and kernel operation takes a guard operand, so every method has
an =_under= twin differing only in that argument. =minocrab-std/src/v3/
kernel.rs= is about half boilerplate for this reason, and =ledger.rs= worse.

It also does not COMPOSE, which is the real complaint. A helper called under
a branch has to thread the guard through its entire call graph by hand;
=send_unshielded= has to know that =is_self= needs a guard, and =is_self=
has to know that =kernel_self_guarded= exists. Nesting two guarded regions
means anding the conditions manually.

What we want:

#+begin_src rust
c.guarded(cond, |c| {
    kernel::inc_unshielded_inputs(c, &token, amount);   // the PLAIN form
});
#+end_src

Implementation is a splice, not an optimisation: emit the body into a
sub-buffer, then rewrite the guard operand on every Impact instruction and
every =public_input= gate as it merges back, anding with any enclosing
guard. The instruction stream is IDENTICAL to what the =_under= form
produces today, which is what makes this safe to turn on everywhere — the
differentials cannot tell the difference, and that is the point.

Deletes: the =_under= half of the ledger and kernel APIs, and the
=_guarded= variants beside them.

** (ii) Constant folding — as normalisation, with the case restated

Fold =copy= of an immediate into its consumers and drop the =copy=. Zero
rows either way (§0a); the value is that it subsumes all five special cases
and future operand positions get it for free.

Consequence worth stating plainly: *the =LedgerRepr= change dmd approved
should not be made.* The pass gives the same output with no trait change and
no churn in the four vault forks. =UnshieldedToken= can go back to being an
ordinary =Either=, and =AnyWire3= can go back to carrying a =Val=.

The =impl Into<Operand>= ergonomics STAY — writing =c.add(x, 1u64)= is nicer
than naming a constant regardless of what it lowers to. What goes away is
its NECESSITY, and the pressure to add another one every milestone.

** (iii) Constraint deduplication — the sleeper

Track, per wire, the tightest =assert_bits= already emitted; drop a later
=assert_bits(w, m)= when =m >= n= for an already-emitted =n=. Sound in that
direction only: a wire constrained to =n= bits satisfies any wider bound,
which is exactly the argument =Uint::widen= already makes for why widening
needs no new constraint.

This is the one that changes what code you can write. Gadgets become able to
assert their own preconditions, so the Borsh layer's "PRECONDITION: already
constrained" comments become checks, and getting it wrong becomes impossible
rather than invisible.

DIVERGES from compactc (which re-emits), so it goes behind the opt profile
with M10's warrant. Rows go DOWN, which is the direction that profile
already wants.

* 3. THE TWO TO REJECT, and why

** Dead code elimination — unsound here without care nobody will maintain

=constrain_bits=, =assert=, =impact= and the transcript gates have no
dataflow consumers. A pass that drops instructions "nothing uses" removes
range checks, and a missing range check is invisible to every differential
test on an honest preimage — the exact failure mode M12 stage 1 centralised
=CircuitArg::constrain= to prevent.

It is implementable with an effectful-op deny-list. It is not worth it: one
row per dead instruction, and we do not emit dead instructions, because the
eDSL only emits what a gadget asked for.

** Common subexpression elimination — needs protocol arguments a pass cannot make

M10 rung i is the proof. The optimised vault reads =kernel.self()= once and
threads it, where compactc reads it at every call site. That IS legitimate —
the address is constant for the transaction and every emitted read still
reconciles through =ResultModeVerify::process_read=, so read count is
"framing, not protocol" — but M10 made that argument explicitly, and still
left =claim= and =completeWithdraw= alone.

A mechanical CSE pass has none of that context. It would dedupe ledger reads
and change the transcript. Where CSE is right it is a TYPED decision, made
in a gadget by someone who can write the soundness paragraph.

* 4. THE GENERAL SHAPE, since it keeps recurring

The wins that actually moved the benchmark — 35-58% in the M10 fork, nine of
twelve k-boundary crossings — came from INSTRUCTION SELECTION: native
=ReverseBytes=, byte-aligned slices instead of per-byte div_mod chains, the
segment-based serializer. Every one needed to know a value was a =Bytes<32>=
with a known alignment.

ZKIR is type-erased. A pass over it sees field elements, so for the
optimisations that matter it is working with strictly less information than
the eDSL has. That is the standing reason to keep OPTIMISATION in the typed
layer and use passes only for things that are genuinely uniform.

Guards are uniform. Constants are uniform. Range constraints are uniform.
Instruction selection is not, and never will be.

* 5. Staging

1. =tests/backend_folding.rs= — DONE, and it is the evidence for all of the
   above.
2. Guard scoping — DONE (additive). See §6.
3. Delete the =_under= / =_guarded= API halves and migrate the 127 call
   sites. NOT started, deliberately: the mechanism lands first and proves
   itself, the churn in three vault ports comes after.
4. Constant folding — DONE (§8). The five special cases are not deleted yet;
   the pass makes them inert first, and removing them is its own commit.
5. Constraint dedup behind the opt profile.

* 6. GUARD SCOPING, as built

=Circuit3::guarded(cond, body)= sets an AMBIENT GUARD for the closure. Three
things pick it up, and the third is why this is a safety feature rather than
a convenience:

1. Impact instructions.
2. Public-transcript reads — so a read inside a scope needs no =_guarded=
   variant.
3. *Assertions.* =assert(x)= inside a scope lowers as
   =assert(select(guard, x, 1))=. By hand this is the caller's job, recorded
   only in a doc comment ("asserts inside the branch are the caller's job"),
   and getting it wrong makes the assertion fire on the branch that was NOT
   taken — which no differential test on an honest preimage can see. That
   bug class is now unwritable inside a scope.

THE GATE, and the reason it is safe to adopt incrementally:
=tests/v3_guard_scope.rs= proves =guarded(g, plain)= is BYTE-IDENTICAL to
the hand-threaded =plain_under(g)= for every shape — Impact ops, reads,
assertions, nesting, and =if_else=. It is a way of writing the guard down,
not a different lowering. All 164 pre-existing circuits are unchanged
(zkir_dump: 0 files differ).

NESTING IS COMPACT'S =&&=, and this is the part that pays. The conjunction
is computed ONCE on entry, and a read between two scopes is guarded by the
OUTER one alone — which is exactly the shape M17's =sendUnshielded= needed
and which I had to reverse-engineer from compactc's artifact to write by
hand. It now falls out of writing the code in the shape of the source.

** ONE SPELLING (dmd, 2026-08-16)

The API arrived at six entry points for one concept — =Circuit3::guarded=,
=if_else=, =when=, =when_value=, =predicate::guarded=,
=predicate::if_else= — which is exactly the sprawl this work exists to
remove. It is now TWO:

| =c.when(cond, body)= | effects. Chain with =.else_when= / =.otherwise= |
| =c.when_value(cond, body)= | a value. =.otherwise= is mandatory and returns it |

- =guarded= is PRIVATE plumbing. It returned the body's value, which invites
  the reading that the value came from a conditional — when in fact it was
  computed unconditionally and only its EFFECTS were guarded. A value that
  depends on a branch has to be SELECTED, which is =when_value=.
- =if_else= is gone: =when(a, ..).otherwise(..)= is byte-identical to it,
  proven before the removal, so it was sugar for a two-arm chain.
- The =predicate::= pair is gone because =Check= implements =GuardCond=, so
  =c.when(eq(x, y), ..)= already works.

AND THE CONSOLIDATION FOUND A BUG. With =when= as the plain-guard spelling,
=c.when(cond, body);= is a statement — and the chain builder was computing
its "nothing matched yet" accumulator eagerly, so a plain =if= with no
=else= emitted a =cond_select= nobody used. Per =backend_folding.rs= an
unused instruction is a REAL ROW and the backend does not drop it. The
accumulator is now computed only when another arm actually arrives, and
=a_bare_when_emits_no_accumulator= pins it.

Worth noting how that was caught: not by review, by the measurement table
from §0 being close at hand.

** dmd's two questions, both yes

*THE PREDICATE VOCABULARY IS THE GUARD VOCABULARY.* =predicate::guarded(c,
eq(a, b), ..)= — =Check='s =and= / =or= / =not= compose into guards for
free, and a comparison's WIDTH is resolved from its operand types in one
place rather than two. A condition is a condition; whether it lands in an
=assert= or in an Impact guard operand is the caller's business.

*IF/ELSE EXISTS*, =Circuit3::if_else= (and the chain below), with the negation
(=select(cond, 0, 1)=, compactc's own =!=) computed once. Both arms emit all
their instructions — a circuit does not branch, so cost is the sum. That is
the setting, not a choice.

** …and the third question: can two nested guards become one statement?

There WAS a =guarded_all(c, &[&|c| .., &|c| ..], body)= — a flat spelling of
nested scopes, each conjunct evaluated under the ones before it. It is
REMOVED (dmd, 2026-08-16), and the reason is better than "redundant".

The flat list hides exactly the fact that matters. The nesting is not
incidental: it IS the short-circuit structure of Compact's =&&=, and in
=recipient.is_left && recipient.left == kernel.self()= the second conjunct
performs a TRANSCRIPT READ that compactc guards by the first. Written
nested, that is visible in the shape of the code. Written flat, it looks
like a list of independent conditions and the evaluation order — the whole
subtlety — is invisible.

So: nest. Two lines and an indent, and the indent is carrying information.

A GENUINELY flat conjunction — =guarded(c, a.and(b), ..)=, both sides
evaluated up front — is available and correct whenever the conjuncts are
PURE. For the self-address case it would mean reading =kernel.self()=
UNGUARDED, which M10 rung i already established is sound (read count is
"framing, not protocol"; every emitted read still reconciles through
=process_read=). That costs the differential and therefore belongs in the
opt profile — which is exactly the split §1 predicts, arriving from a
direction nobody planned.

** …and the fourth: an if / else-if / else CHAIN

=c.when(a, ..).else_when(b, ..).otherwise(..)=, arms MUTUALLY EXCLUSIVE —
arm /n/ runs where its own condition holds and no earlier one matched.

The mechanism is one accumulator wire, "nothing has matched yet". Arm /n/'s
guard is =unmatched && cond=; the accumulator then becomes
=unmatched && !cond=, which is ONE =cond_select= rather than a negate and an
and (=select(cond, 0, unmatched)=). So two selects per arm after the first,
and BOTH ends are free: the first arm's guard is its condition, and
=otherwise='s guard is the accumulator itself.

Falls out of that: a two-arm chain is EXACTLY =if_else=, one negation and no
more (=a_two_arm_chain_is_if_else= pins it). And a chain nests inside a
guard — its arms conjoin with the ambient one, so an if/else-if inside a
branch needs no threading either.

Arms return =()=, deliberately. A circuit does not branch, so every arm's
instructions are emitted regardless and "the value of the branch that ran"
is not something the stream can express; build it with =cond_select= on the
arms' results, where the selection is visible and priced.

** …and the fifth: the chain as an EXPRESSION

=c.when_value(a, ..).else_when(b, ..).otherwise(..)= returns a value —
Compact's =if= as an expression. dmd asked for it knowing it is expensive,
and wanted the cost stated rather than the feature withheld. Both are done;
the cost is in the method's own docs, where a caller will meet it.

EXHAUSTIVE BY CONSTRUCTION, which the effectful form does not need and
cannot have: =otherwise= is the only method that returns the value, so a
value chain without a fallback does not compile. An arm that does not run
simply has its effects guarded off; a value has to come from somewhere.

THE COST, stated honestly in three parts:
- Every arm's instructions are emitted regardless. An =if= costs the SUM of
  its arms, never the maximum. That is the setting, not this API.
- One =cond_select= per NATIVE SLOT of the result, per arm — so a
  =Bytes<32>= is two, and a =Maybe<T>= selects its tag as well as its
  payload. =Select= is the trait, implemented for the typed leaves.
- The two selects the guard accumulator already costs.

AND WHAT IT DOES NOT COST: anything over the hand-written form.
=a_value_chain_is_the_hand_written_select= pins that — the selects are the
ones a careful author writes anyway. What the abstraction removes is
selecting on the wrong guard, and the temptation to skip guarding the arms'
EFFECTS because only the value looked conditional
(=a_value_chain_still_guards_effects=).

So the recommendation is not "avoid it". It is: reach for it when the
branches genuinely produce a value; reach for straight-line code and one
=cond_select= at the end when one arm is much dearer than the other and you
would rather pay for that arm once, unconditionally.

=otherwise= returns =Selected<T>= (dmd, 2026-08-16) — =repr(transparent)=,
=Deref= to the value, =Copy= where the value is, =into_inner()= to be rid of
it. Field access needs no ceremony: a =Selected<B32>= still has =.hi=.

It exists for one reason a function-level =#[must_use]= cannot serve. A
function attribute fires only where the call is WRITTEN; a must-use TYPE
fires wherever a value of it is dropped — including one step removed, which
is where the waste actually happens:

#+begin_src rust
fn fee(c: &mut Circuit3, ..) -> Selected<Uint<64, Public>> {
    c.when_value(..).otherwise(..)     // fine, it is returned
}
fee(&mut c, ..);                        // …and THIS is the mistake
#+end_src

A compile_fail doctest on =Selected= pins exactly that shape.

THE TENSION, recorded because it decides how much the wrapper is worth: the
more eagerly it is unwrapped, the less it propagates. Kept in a helper's
SIGNATURE it catches the dropped-result mistake a caller away; unwrapped at
the first opportunity it degrades to the function-level attribute it
replaced. Both are acceptable — the type also reads as documentation at
every use site ("this came from a branch, so every arm was paid for") — but
the LINT only pays if signatures keep it. That is a convention question for
the ported contracts, not something the type can enforce.

NOT CLAIMED: that an /n/-arm chain matches compactc's lowering of an
=else if= ladder. No fixture exercises one, so the two-arm case is checked
against =if_else= and the /n/-arm case against a hand-written expansion.
That gap is worth a fixture when a corpus contract needs it.

A GENUINELY flat conjunction — =guarded(c, a.and(b), ..)= with both sides
evaluated up front — is available and correct whenever the conjuncts are
PURE. For the self-address case it would mean reading =kernel.self()=
UNGUARDED, which M10 rung i already established is sound (read count is
"framing, not protocol"; every emitted read still reconciles through
=process_read=). That costs the differential and therefore belongs in the
opt profile — which is exactly the split §1 predicts, arriving from a
direction nobody planned.

* 7. EVIDENCE FROM M17's SHIELDED PORTS (2026-08-16)

Three ports written to compactc's own instruction stream, and every place
they could NOT go through the ergonomic API is evidence for §2. Recorded
here because it arrives from a direction §1 did not anticipate: not "the
backend already folds this", but *the surface API can only be as ergonomic
as the lowering allows, while the bar is instruction equality*.

1. *=!b= is a =cond_select=, not our =not=.* compactc has no boolean-negation
   opcode; it emits =cond_select(b, 0, 1)=. =minocrab_std::v3::kernel= has
   carried a private =not= of exactly that shape since stage 2, and the
   shielded ports use it twice more. Our =Circuit3::not= emits ZKIR's =Not=,
   which is correct, one row, and never what compactc writes.

2. *=&&= is a =cond_select=, and =predicate::and= is a =mul=.* Both are right
   on booleans and both cost one row. But a circuit that must match
   instruction for instruction cannot use the predicate vocabulary for a
   conjunction, so =bytes_eq= and =is_self= hand-write the select.
   Note this one is NOT a pass's job: =mul= on two arbitrary field elements
   is not a select, so a pass over type-erased ZKIR may not rewrite it. It is
   a TYPED decision — =Check::and= knows its operands are booleans — and
   therefore §4's rule says it belongs in =predicate.rs=. Changing it would
   move instructions (not rows) in every circuit that guards through
   predicates, so it wants its own commit and its own dump diff.

3. *A folded tag beats a chain.* =sendShielded= ends in Compact's =if= as an
   expression, which is what =when_value= is for, and it still cannot use it:
   compactc folds the =Maybe='s tag into the else-arm's guard, because
   selecting between the constants 0 and 1 IS that guard. The chain would emit
   the select a second time. Constant folding (§2 ii) does not fix this one
   either — the inputs are constants but the SELECT is what has to disappear,
   which is a peephole on =cond_select(b, 0, 1)= → the guard wire itself.

So §2(ii) grows a sibling worth naming: a *boolean normal form* — fold
=cond_select(b, 0, 1)= to =b='s negation-of-record and recognise the shape
when it is asked for a second time. Cheaper than it sounds, because there are
only two spellings in play and both are already written down here.

MEASURED, since both classes now have a number
(=minocrab-sim/examples/opcost.rs=, new cases): 100 =copy=s of an immediate
cost ZERO rows; 100 =cond_select=s cost 101. So constant folding (§2 ii) is
worth exactly its instruction count and no rows — which §0(a) already said —
while a select that a fold could remove is one row each. Both remain small;
the case for the passes is API surface, not cost, exactly as §2 argues.

* 8. CONSTANT FOLDING, as built (2026-08-16)

=minocrab_ir::v3::passes::fold_immediate_copies=, run by =Builder3::finish=
so every circuit gets it: a =Copy= of an immediate is substituted into its
consumers and dropped. 768 =copy= instructions removed across 91 of the 167
workspace circuits; the other 76 had none. Zero rows, as §0(a) measured —
row_snapshot is bit-identical and the interface snapshot untouched.

** §1's table was WRONG, and the fixture that proved it

The table said constant folding CONVERGES on compactc. It does not:
*compactc names some of the constants it inlines elsewhere*, and the naming
is driven by its own frontend rather than by any operand-position rule.
M17's =sSendShielded= is the counterexample —
=upgradeFromTransient='s zero high limb is emitted as =copy 0x00= and then
used BOTH as a hash operand and, through a =cond_select=, as an output. An
always-on fold makes us strictly MORE inlined than compactc, which costs the
instruction-for-instruction fixtures.

An "all uses are operands" rule does not save it (that was tried first: the
change coin's zero limb reaches the output only through a select, so the rule
folds it and the fixture still fires). The naming is not a property of the
ZKIR at all.

*THE RESOLUTION*: the four instruction-for-instruction differentials
(=kernel_tokens=, =adts=, =bounded=, =opaque=) run the SAME fold over
compactc's artifact before comparing. Their criterion becomes "identical
instruction for instruction, MODULO the naming of constants" — and that is a
precise, mechanically defined relation rather than a weaker one: everything
else still compares exactly, the normaliser is the pass itself (one
definition, not a test-local approximation), and a =copy= of an immediate is
a rename with zero rows, no public input and no semantics. *This is the one
judgement in the pass that is dmd's to veto.*

** What it bought, immediately and without being asked

- =opaque_differential= lost its bespoke =without_named_immediates=
  normaliser, its =NAMES_A_LITERAL= list and a whole test that counted the
  extra =copy=s. All fourteen circuits are now equal on the same criterion as
  each other. M15 left that gap open pending an API change to =LedgerRepr=
  that all four vault forks depend on; *that change is now unnecessary*,
  which is §2(ii)'s prediction landing exactly as written.
- =erc20_vault_modern='s divergence ledger collapsed to =Twin::Identical=
  for ALL NINE circuits. M9 phase 8's showcase twin differed from the borsh
  fork in precisely one class of instruction — the =Copy=s that named a
  constant — so the ergonomic rewrite is now free at the IR level rather
  than merely PI-equivalent. Five are byte-identical; the other four agree
  up to identifier NUMBERING (a removed copy still consumed its number), so
  that ledger's test canonicalises names like every other differential.

** The one thing the fold broke, and what it says about disclosure

A disclosed constant had no identifier left to resolve, so the valued
disclosure report read =<not computed>=. =Disclosure3= now carries
=DisclosedWire::Named(Identifier) | Constant(Fr)= and the simulator resolves
the second directly. That is better than what it replaced: a constant's value
was never in doubt, and the record now says so instead of pointing at a wire.

** NOT DONE

The five special cases are inert but still present: M9 phase 7's operand
positions, M9 phase 8's inlined guard, M16's =AnyWire3::immediate=, M17's
=UnshieldedToken= and =token_type=. Deleting them is mechanical, touches the
vault forks, and belongs in its own commit with its own dump diff — the
=impl Into<Operand>= ergonomics stay either way (§2 ii), what goes is their
NECESSITY.
