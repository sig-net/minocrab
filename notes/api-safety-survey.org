#+title: M19 — API safety survey: footguns, wrong code, and what the types could hold

Commissioned by dmd 2026-08-16, three questions:

1. *Footguns* — where a Rust programmer thinks the compiler or the build
   guarantees something it does not. (Hard to use is fine; failing after
   typecheck but before deploy is fine.)
2. *Wrong code* — where we generate something SEMANTICALLY DIFFERENT from the
   equivalent Compact.
3. *Invariants the type system could hold* instead of the programmer.

* 0. METHOD, and why it found things

Two seams, both chosen because they find the errors that TESTING CANNOT.

*(a) Invariants stated in prose.* A doc comment that says =PRECONDITION=,
"the caller's job", "must already be" is an invariant somebody decided not to
check. Grep is a complete enumeration of them, and every hit is a candidate
by construction.

*(b) Compact's own lowering rules, from notes/builtin-lowering.org §9* —
which were read out of compactc's source and VERIFIED against artifacts. Any
rule compactc applies automatically and we leave to the author is a semantic
divergence, whatever the differentials say: a differential runs one honest
preimage through both sides, and a missing guard is invisible on honest
input. That is not a hypothesis. THREE bugs of exactly this class were found
and fixed in the session that commissioned this survey — guarded witnesses
consuming the private transcript on the untaken branch, unguarded assertions
firing on the branch not taken, and a literal silently outside its operand's
bound. All three were green on every differential the day before.

*The prior this establishes:* look where a test on well-formed input cannot
see the error. Everything below is found that way.

* 1. WRONG CODE (question 2), most severe first

** B1. SUBTRACTION HAS NO UNDERFLOW GUARD, AND COMPACT'S DOES — /the finding/

Compact, verified (=infer-types.ss=, quoted in builtin-lowering.org §9):

#+begin_quote
=-=: inserts an explicit guard *before* the subtraction:
=assert(a >= b, "result of subtraction would be negative")= with
bits = max(1, intlen(max(maxa,maxb))), then field subtraction lowered as
=neg(b)= + =add(a, neg)=.
#+end_quote

MinoCrab: there is no subtraction. An author writes =c.add(a, c.neg(b))=,
which is compactc's lowering *with the guard removed*. Nothing emits the
assert and nothing asks for it.

This is not theoretical. =erc20_vault_modern= line 1204-1219 is the vault's
one subtraction, and it carries a HAND-WRITTEN guard with a comment that
names the risk:

#+begin_src rust
// The subtraction's guard, and the most dangerous arithmetic in the
// contract: the attested spend cannot exceed what was surrendered.
c.assert(amount_in_u.le(amount_in_max_u).message("Attested amountIn exceeds amountInMaximum"));
let neg_in = c.neg(amount_in);
let change = c.add(amount_in_max, neg_in);
#+end_src

The comment is correct and the code is correct. The problem is that *both are
optional*. Delete the three assert lines and every test still passes: the
differentials run honest preimages, the spec harness generates
=amount_in <= amount_in_max= because that is what the spec says, and the
adversarial sweeps were written from the same understanding.

WHAT AN UNDERFLOW PRODUCES, since "negative" is the wrong intuition: field
arithmetic has no sign. =a - b= for =a < b= is =a - b + p=, a value near
2^255. Not −1. So downstream it is not a small wrong number, it is a coin
worth ~2^255, or a =Uint<64>= ledger write of a 255-bit value, or a
=less_than(_, _, 64)= over a 64-bit window of a 255-bit number.

*This is the balance-underflow bug, and our API makes it easier to write than
Compact does.* Compact's author cannot forget; ours must remember.

FIX — *BUILT, same session.* =Uint::sub(c, other)= and
=Uint::sub_with(c, other, message)= emit exactly compactc's
=assert(a >= b)= + =neg= + =add=, in that order, at compactc's width (the
comparison's bits come from =BITS= through the predicate layer, not from a
number typed at the call site). The result keeps =BITS=, which is compactc's
rule (=Uint<maxa>=) and is sound because =a - b <= a < 2^BITS=.

=sub_with= exists because the message is what makes a failed proof
diagnosable: the vault's hand-written guard said "Attested amountIn exceeds
amountInMaximum", which is better than compactc's generic text, and losing it
would have been a reason not to adopt the guarded form.

THE PROOF IS BETTER THAN A UNIT TEST, and this is the part worth keeping: the
vault's own subtraction — its ONLY one, in =completeSwap= across all four
artifacts — was ported to =sub=, and *the ZKIR dump did not move*. Two of
those artifacts are instruction-mirroring against compactc's own
=completeSwap=. So the claim "=Uint::sub= is compactc's subtraction" is
checked against a real compactc artifact, not against a twin we wrote.
Three unit tests pin the rest: identity with the hand-written guarded form,
that the raw spelling emits NO assert and the typed one does (so a future
"optimisation" that drops the guard fails there), and that the width comes
from the type.

The raw =c.add(x, c.neg(y))= stays — the ports may need it — but it is now
the unusual spelling rather than the only one.

** B2. NO MAX TRACKING, SO NO DOWNCAST CHECK ON =+= AND =*=

Compact, same source:

#+begin_quote
=+=, =*=: plain field =add= / =mul=, result type =Uint<maxa+maxb>= resp.
=Uint<maxa·maxb>= … *no overflow check at the op itself*; the check happens
only when the value is later downcast (assignment to a declared =Uint<N>=
inserts =downcast-unsigned= → a range constraint).
#+end_quote

So Compact's safety on =+= is entirely in the DOWNCAST. Its types carry max
values and propagate them, and the moment a widened value is stored into a
declared type the constraint appears.

MinoCrab tracks nothing: =c.add= returns =Wire3<FieldT>=, which has no max
and no width. Re-entering the typed world is =Uint::<64>::from_field(sum)= —
an unchecked assertion (see A1). *The downcast that is Compact's entire
overflow story does not exist here.*

=Uint<BITS>= is not the same as Compact's =Uint<maxa+maxb>= tracking, so this
is not a like-for-like fix; the honest version is a =BoundedUint=-style max
carried through arithmetic, which is what =BoundedUint<BOUND>= already is.
=BoundedUint= arithmetic that computes the result's bound at the type level
(=BoundedUint<A> + BoundedUint<B> -> BoundedUint<A+B-1>=) is Compact's rule
exactly, in const generics, and the downcast is then =to_uint= /
=constrain_input=, which already range-checks.

** B3. THE BORSH LAYER'S INJECTIVITY IS A DOC COMMENT

Three sites (=Serializer=, =BorshReader::take=, =hash::persistent_hash=) all
say the same thing:

#+begin_quote
PRECONDITION: every pushed wire must already be constrained to its byte
length … the limb packing is only injective for in-range segments.
#+end_quote

=hash.rs= states the consequence itself: *"Without that the packing is not
injective and the digest binds nothing."*

A digest that binds nothing is a signature that verifies over a preimage the
prover chose. This is the most severe consequence in the survey; it is third
only because reaching it requires a caller to push an unconstrained wire,
where B1 requires a caller to forget a line.

Not a divergence from Compact — the note records that compactc's byte-wise
form has the same property (an explode chain leaves its top byte
unconstrained). But "no worse than Compact" is the wrong bar for a
precondition that nothing checks and whose violation is invisible.

FIX: this is exactly what notes/ir-passes.org §2(iii) (constraint dedup) was
designed to enable — with a deduplicating pass, the gadget can constrain its
own inputs and the redundant constraint costs nothing. The precondition
becomes a check. §0(b) of that note already measured the price of the
alternative: a repeated =constrain_bits= is 2 rows, the most expensive
redundancy measured, which is why the comments exist.

** B4. STDLIB HELPERS TAKING RAW =Wire3= WHERE COMPACT SAYS =Uint<64>=

=common::mint_shielded_token(c, domain_sep, value: Wire3<FieldT, Public>, …)=
against Compact's =mintShieldedToken(domainSep, value: Uint<64>, …)=. The
Compact signature rejects a 128-bit value at the call site (the caller must
write =amount as Uint<64>=, whose downcast range-checks); ours accepts any
field element.

The vault is safe because it asserts =amount <= u64::MAX= by hand, mirroring
the Compact source, which asserts it too. But the Compact source's assert is
a nice error message on top of a cast that would fail anyway; ours is the
only thing standing there.

Note the typed kernel layer gets this RIGHT — =kernel::mint_shielded= takes
=Uint<64, Public>=. The raw-wire signatures are the contracts-level helpers
in =minocrab-contracts::common=, i.e. the older layer.

*FIXED same session*, against Compact's own declaration rather than an
inferred one: =standard-library.compact:122-125= says
=mintShieldedToken(domain_sep: Bytes<32>, value: Uint<64>, nonce: Bytes<32>,
..)=, and all four =value: Wire3<FieldT, Public>= parameters are now
=Uint<64, Public>=.

WHAT IT DOES NOT BUY, said plainly: the narrowing is still not CHECKED. The
caller writes =Uint::<64, Public>::from_field(amount)=, which is A1's
unchecked assertion wearing its own name. What changed is that the claim is
now WRITTEN at the call site instead of a 128-bit wire sliding into a 64-bit
parameter in silence. Making it checked is A1's fix.

CORRECTED BY THE REVIEW (2026-08-16), in two parts, both artifact-verified:

1. The =assert(amount <= u64::MAX)= justification is LOCAL only for the
   request circuits (deposit, withdraw, swap — swap bounds BOTH its amounts,
   =erc20-vault.compact:801-802=). At the four SETTLE mints (claim,
   completeWithdraw, refund, completeSwap) the decoded word is bounded only
   to =< 2^128= locally; the =Uint<64>= claim there rests on the fact that
   every record in the map was written by a request circuit that bounded it
   — a WHOLE-CONTRACT argument, not a local one. The =from_field=s at those
   four sites are exactly A1's shape and should be first in line when A1's
   constrained twin exists.

2. *COMPACTC EMITS NO CHECK FOR A CAST IN ARGUMENT POSITION.* The source
   writes =amount as Uint<64>= at all four settle mints, and the artifacts
   contain no 64-bit constraint anywhere between the decode and the mint —
   the ONLY 64-bit op in claim/completeWithdraw/refund is the
   =initialized >= 1= counter guard (checked instruction by instruction in
   the dumps). So notes/builtin-lowering.org §9's downcast rule
   ("assignment to a declared =Uint<N>= inserts downcast-unsigned") does
   NOT extend to argument-position casts, at least in this compiler version
   at these sites. Compact's own safety here rests on the request-time
   guards — i.e. Compact has the same whole-contract dependency our
   =from_field= has, it just never wrote it down. Worth carrying into fix
   1's design: =BoundedUint::to_uint= is exactly the place OUR api can be
   stricter than Compact by emitting the check compactc omits.

* 2. FOOTGUNS (question 1)

** A1. =from_field= IS AN UNAUDITED =unsafe=, AND IT IS THE HOLE EVERY OTHER
   SOUNDNESS ARGUMENT LEAKS THROUGH

Every typed leaf has one:

#+begin_src rust
Uint::<8, Private>::from_field(w)   // "wrap a wire already known to hold a Uint<8>"
#+end_src

It emits nothing. It is a *claim*, and the claim is what
=CheckOperand::BITS=, =CheckOperand::MAX= (added this session), the
comparison widths, =widen='s soundness argument and the Borsh packing all
rest on.

A Rust programmer reads =Uint<8>= as a type with an invariant — that is what
the newtype pattern MEANS in Rust, and this codebase has trained them to
believe it, because `disclose` really is enforced, visibility really is
enforced, and `Guarded` really is enforced. `from_field` is the one place
where a type says something the build does not check, and it does not look
different from the ones that do.

Usage: 80 sites in minocrab-std, 16 in contracts. Most are safe (the value
came from a constrained argument or a checked instruction) — but "most" is
established by reading, not by anything mechanical.

WHY IT CANNOT SIMPLY BE DELETED: it is the constructor the =CircuitArg=
machinery uses on the way in, before =constrain_input= runs. The obligation
is real and the escape hatch has to exist.

FIX, and the precedent is in this repo: *make it look like what it is.* The
disclosure escape hatch is =disclose(w, label)= — greppable, labelled,
carried into a report, and enforced by generated tests. =from_field= should
be the same shape: named so it reads as an assertion
(=from_field_unchecked=), and where a constrained twin is possible
(=from_field_constrained(c, w)= emitting the range check) that twin should be
the short name. Zero rows for the rename; the constrained twin costs exactly
the constraint it emits, which is the point.

** A2. =.field()= DISCARDS THE OBLIGATION SILENTLY, AND IT IS EVERYWHERE

174 calls in the contracts crate. Every one converts a leaf whose type
carries a range into a raw wire that does not. Nothing marks the loss, and
the round trip =x.field()= → arithmetic → =from_field= is precisely the B1/B2
path.

This is not an argument for =Deref= (see the Deref survey the same session:
=Deref= would make the loss INVISIBLE rather than merely unmarked). It is an
argument for typed arithmetic — if =a.sub(c, b)= and =a.add(c, b)= exist,
most of the 174 disappear and the ones that remain are genuinely leaving the
typed world.

** A3. WHAT THE SESSION ALREADY CLOSED, recorded so the pattern is visible

Three, all found in one day, all invisible to every differential:

- *guarded witnesses* consumed the private transcript on the branch NOT
  taken (fixed: the ambient guard reaches witnesses);
- *assertions inside a branch* were the caller's job, recorded only in a doc
  comment (fixed: an assert inside a scope lowers as
  =assert(select(guard, x, 1))=);
- *guarded reads* handed back the type's default with nothing saying so
  (fixed: =Guarded<T>= — 19 sites had to say =.or_default()=);
- *a literal outside its operand's bound* made a comparison constant (fixed:
  =CheckOperand::MAX=).

Every one of these was a doc comment before it was a check. That is the
pattern, and §0(a) is how to keep finding them.

** A4. SMALLER, LISTED WITHOUT ARGUMENT

- =c.assert(w)= on a raw wire: Compact's =assert= takes a =Boolean=; ours
  takes any wire. CHECKED, and it is NOT the silent footgun it looks like —
  the reference VM rejects a non-boolean condition outright
  (=operand_bool=: "expected boolean, found: …"), so the failure is at
  simulation/proving time rather than at typecheck. By dmd's own bar
  ("errors after typechecking but before deploy are fine") this is
  acceptable, and it is listed only so the next reader does not re-open it.
  The residual cost is that the error arrives later than a =Bool<V>=
  parameter would make it.
- The =_with= family (=mint_shielded_token_to_key_with=, =burn_coin_with=,
  =receive_shielded_with=) took a =me: B32<Public>= the caller promised was
  =kernel.self()=. Nothing checked it. Passing the WRONG address mints to
  the wrong contract. (M18's note calls this memoization; it was memoization
  with an unchecked key.)
  *FIXED, and it needed no new type.* The parameter is now
  =ContractAddress<Public>=, which only =kernel::self_address= and its
  guarded twin produce — so an arbitrary =B32= no longer type-checks there.
  The address flows typed through =record_and_notify= and =notify_signet= as
  well, and =.bytes()= is the one place it becomes raw again. Zero rows (the
  wrapper is =repr(transparent)= over the same limbs); dump unchanged.
- =LedgerCell<T>::write= of a value wider than =T='s atoms: the atom list
  comes from the type (good) but the VALUE is not re-checked against it.
- =Circuit3::copy= is documented as "not a way to make a value cheaper" —
  which is a hint that somebody will try.

* 3. WHAT THE TYPES COULD HOLD (question 3), ranked by value

1. *Typed arithmetic with Compact's guards.* =sub= emits the underflow
   assert; =add=/=mul= on =BoundedUint= compute the result's bound at the
   type level, so the downcast is where the range check appears — Compact's
   rule, in const generics. Closes B1 and B2 and most of A2.
2. *Constrain-on-construction, with a dedup pass making it free.* Closes B3,
   and turns every "PRECONDITION" comment in the Borsh layer into a check.
   This is ir-passes step 5, already designed and measured.
3. *=from_field= renamed to what it is*, with a constrained twin taking the
   short name. Closes A1 by making it visible; zero rows.
4. *The Compact signature types on the contracts-level helpers.* Closes B4,
   mechanical.
5. *A =SelfAddress= newtype* so =_with= cannot be handed an arbitrary
   =B32=. Closes the sharpest edge of A4.

* 4. WHAT THIS SURVEY DOES NOT COVER

Stated so the gaps are known rather than assumed:

- The =minocrab-ir= / ZKIR boundary. Everything here is above it.
- Cross-contract call argument marshalling, beyond noting that =CallArg= and
  =CircuitArg= share their constraint path (which is the good case).
- The macros' generated code, which the thinness tests cover for SHAPE but
  not for these properties.
- Anything about the proving system.
