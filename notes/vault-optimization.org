#+title: M10 pre-work: what the vault's remaining cost is, what the protocol pins, what can move

Analysis of record for M10 (Opus survey agent, 2026-08-15; supervised
session). Nothing here is implemented yet. Verdicts marked UNSURE must
be resolved before acting on anything that depends on them.

* Headline finding — M10's premise corrected
notes/benchmark.org says the remaining vault cost is "PI-coupled". True
about LOWERING (no instruction-selection change reaches it), misleading
about ROWS: reconstructing per-circuit budgets from the frozen row
snapshot shows 95-99% of every vault circuit's rows are SHA-256,
keccak-256 and secp256k1 ECDSA. The entire Impact-op stream, every
public_input/popeq embed, every constrain_bits, select and assert
together are 370-2,000 rows per circuit (1-4%).
The region profiles attribute by INSTRUCTION COUNT, which inverts the
picture (claim's ecdsa region: 12.6% of instructions, ~53% of rows;
its keccak: 1.0% of instructions, ~9% of rows).
Consequence: constrain_bits dedup / transcript framing / serialization
— what the M10 milestone text was written around — is worth a few
hundred rows per circuit and crosses NO k boundary. The real leverage
is WHICH HASH CONSTRUCTIONS THE VAULT CHOOSES: a spec-level question.
SHA-256 pair-hash = 3,760 rows; keccak block = 4,220; ECDSA = 25,140.

Mechanism confirmations (all measured, none assumed):
- SHA-256 blocks = ceil((len+9)/64) — the 55→56 and 119→120 steps move
  the block count with the per-block cost flat.
- keccak blocks = floor(len/136)+1 — the 135→136→137 steps.
- Poseidon's unit is the PERMUTATION, rate 2: 1 and 2 limbs both cost
  20, 3 and 4 both ~41. "Per limb" is a fiction that happens to average.
- Cost is FLAT IN k. Every shape is priced twice, in a minimal circuit
  and in one padded to ~35k rows; nothing moved by >5%. The analysis's
  "at k=16 a 248-bit check ≈ 17 rows" is wrong — it is 62 rows at every
  size (4 bits per row, =nr_pow2range_cols = 4=). Each check is thus
  ~3.6× the analysis's estimate — claim's whole top-level region (16
  constrain_bits among 36 instructions) is ~499 rows, 1.1% of the
  circuit. Still ≤4% of any circuit, still no k crossing, still not
  worth the soundness surface: the "do not dedup" verdict is unchanged.

* Pin taxonomy
Framing: the M10 artifact is necessarily a SEPARATE DEPLOYMENT
(different verifier key ⇒ different ContractOperation ⇒ different
address). Compatibility means exactly: (1) the deployed ledger/Impact
VM accepts the tx; (2) the deployed Signet singleton accepts the
cross-contract call and the MPC can read/derive/sign/attest; (3) our
off-chain twins regenerate (never a constraint).

** (a) PROTOCOL-PINNED (immovable)
- Impact op streams (opcodes/paths/values/popeq embeds/guard blocks),
  ~200-800/circuit: the PI vector IS Op::field_repr of the transcript;
  the verifier builds PIs from the tx's own transcript
  (ledger/src/verify.rs:1946-1959). The SET of state changes is
  discretionary; the encoding of each is not.
- public_input + popeq read framing (~100-200/circuit): one op per
  read, one FAB limb per gate (onchain-vm/src/result_mode.rs:44-62).
  popeq embeds CANNOT merge; public_input gates CANNOT batch. Fewer/
  wider READS is the only lever (see state layout, class c).
- Cross-contract call machinery to the singleton (~150): comm =
  poseidon([cc-rand] ++ callee-FAB args ++ results); ledger matches
  (addr, ep-hash, comm) against a real ContractCall
  (structure.rs:2722-2745), comm always PI #2. The singleton is
  deployed compactc output — its layout/hashes are fixed by ITS
  artifact.
- keccak request id + record field order/widths (12,900 / 22,070): the
  MPC decodes the record from raw ledger state; Signet.compact states
  the field order is relied upon. (See UNSURE on whether the MPC
  re-verifies the id — default verdict PINNED.)
- keccak attestation digest (~4,280): it is what the MPC signed; already
  1 block.
- in-circuit secp256k1 ECDSA (25,140): the only authentication gate;
  MPC is secp256k1-native.
- tokenType(domainSep, self) (3,760/use): ledger derives the colour
  itself (coin-structure/src/contract.rs:58-68, used verify.rs:856-865)
  and balances it against the offer's coins.
- coin commitments/nullifiers (5,640/use): multiset equality against
  the offer (verify.rs:1517-1558, 1596-1608); preimage layout is
  zswap's.
- do_communications_commitment = true (~30): comm hard-coded at PI #2.
- notification payload naming the map's ledger path (~5): the MPC
  follows it (path VALUE may change with the layout; must agree).

** (b) COMPACTC-FRAMING-ONLY (freed by dropping artifact PI-equality)
- Repeated kernel.self() reads (~11× across the vault; ~100-250/circuit
  freed): how many times we emit the read is our choice; each emitted
  read still reconciles.
- Uncached-vs-cached idx opcode choices (tens): both valid on-chain;
  cached after idxp is cheaper in ops and gas (compactc hard-wires
  f-cached #f, reduce-to-zkir.ss:622).
- compactc's unfolded cond_select pairs (tens).
- Instruction ordering/copies (tens-low hundreds): mostly harvested;
  M9 phase 7 inline immediates take the rest.

** (c) SPEC-DISCRETIONARY — the real M10 space
- vaultTokenDomainSeparator = SHA-256([pad("erc20:vault:"), erc20]):
  −3,760 × 9 uses. Ledger accepts an ARBITRARY 32-byte pre_token.
  Replace with injective non-hashed encoding (0x01 ‖ zeros ‖ erc20).
  No new disclosure (separator already public in the mint op; erc20
  already public in the record) — log it anyway.
- userCommitment = SHA-256 over 64 bytes: −~3,570 × (initialize,
  deposit, claim). MPC treats path as 32 opaque bytes. Poseidon ≈ 45
  rows + ~130 div_mod. (Or stay SHA with ≤55-byte preimage → 1 block,
  −1,880.)
- withdrawRefundCommitment = SHA-256 over 96 bytes: −~3,700 × 6 uses.
  Purely internal (written then compared). Poseidon; storing as Field
  cell drops the split too (see UNSURE on Field-typed map values).
- changeNonce = persistentHash([mintNonce, pad("change")]) in
  completeSwap: −3,760. Nonce needs uniqueness only; mintNonce is
  caller-chosen + disclosed; mintNonce+1 (or Poseidon) equivalent.
- refund's two branches compute the same mint twice: −~9,430.
  Instructions cost rows unconditionally (guards gate PI emission
  only); both routes feed an identical domainSep→tokenType→coinCm→mint
  block and compute the identical refund commitment. cond_select the
  inputs, run the block once, keep ledger ops guarded per route.
- Ledger state layout: −200-400/circuit + smaller PI vector. Only
  field 0 and the notification path are named by protocol;
  vaultEvmAddress/evmChainId/caip2Id/uniswapRouter/initialized can
  share one Cell<struct> → one idx+popeq instead of five.
- constrain_bits on arguments: −150-250/circuit — DO NOT TAKE, see
  verdict below.

** Q1 burn restructure — FEASIBLE (avenue 6 CLEARED; land it FIRST among risky)
claimed_shielded_spends is keyed (u16, Commitment) with NO contract-
address component (verify.rs:1559, 1582-1608): a claimed spend needs
only "commitment exists in this segment's offer, unclaimed by another
contract". Receives equality (strict, contract-associated only,
verify.rs:1489-1557) and nullifier equality (verify.rs:1503-1535) are
satisfied vacuously because shieldedBurnAddress() is left(default) =
Recipient::User → contract_address: None. Shielded claims contribute
NOTHING to the balance equation (verify.rs:736-920); value destruction
is enforced by the offer's Pedersen balance + the circuit's colour/
value constraints. Proven precedents in the pinned suite: micro-dao.rs
:840-953 (contract claims spend of a user-recipient output),
composable.rs:1311-1315 (spend claim of ANOTHER contract's output),
token_vault_shielded.rs:432-535. Off-chain: the burn Output is the
same ZswapOutput the vault already builds (no ciphertext needed);
segment routing already keys on spends ∪ receives (construct.rs:
163-175). Replay: global CommitmentAlreadyPresent (zswap/ledger.rs:
100-104) — same gate as today, but now the ONLY one (nullifier set no
longer a second gate; note in deviation log).
New harness obligations replacing what receiveShielded gave for free:
(1) exactly one ClaimSpend per burn, ClaimReceive/ClaimNullifier
empty; (2) the commitment is coinCommitment(constrained coin, left(0));
(3) adversarial: second contract claiming the same commitment rejected;
(4) off-chain twin emits the burn Output with no createZswapInput.
Honest gap: no pinned test has a contract claim a spend with NO
contract-owned input in the tx — add a local well-formedness test
against the pinned ledger (mirror micro-dao.rs:840-960) BEFORE landing.
Bonus: drops one Transient (two zswap proofs) — smaller tx, lower fee.

** Q4 Poseidon durability — SPLIT (the important negative finding)
Midnight's own guidance quoted: persistent_hash "guaranteed for
long-term support" (base-crypto/src/hash.rs:92-95); transient_hash
"may be changed on hard-forks" (transient-crypto/src/hash.rs:75-81);
zkir spec: persistent for "standard, stable hash across contexts".
Midnight's own Dust subsystem stores Poseidon in fund-bearing
long-lived state, so the pattern isn't forbidden — the question is
per-value recompute-later exposure:
- withdrawRefundCommitment (avenue 3): CLEARED. Internal, one
  round-trip window, never leaves the contract. Poseidon fine; log it.
- userCommitment (avenue 1): NOT CLEARED as written. It is the
  request PATH, which feeds the MPC's derivedSigningKey
  (Signet.compact:78-85) and therefore determines the user's real
  derived EVM account. A hash change makes the sk→path mapping
  unrecomputable → ERC-20 at the old derived address stranded FOREVER
  (redeployment does not rescue it: with SHA a redeployed vault honours
  old commitments; with Poseidon-over-BLS12-381 it cannot). The "MPC
  treats path as opaque" aside is true and irrelevant — the hazard is
  the sk→path mapping's stability. SUBSTITUTE: keep SHA-256, shrink
  the preimage to ≤55 bytes (1 block): −1,880/use, zero exposure.
  Deposit's k14 does NOT depend on Poseidon; initialize lands k12
  instead of k10 — documented trade. Full Poseidon there would need an
  affirmative sig-net answer (same artifact as Q2).

* constrain_bits dedup — analyzed, rejected
At k=16 a 248-bit check ≈ 17 rows; suite budget ~1,600 rows total.
Directly-written values are implicitly bounded by their FAB atom on
chain — but almost nothing goes to state raw: amount reaches the
transcript via numericAbiWord, so its 128-bit bound is what makes the
derivation sound (dropping it = over-mint soundness bug, not a compat
bug). And the communications commitment does NOT imply input
canonicity for root calls: ContractCallPrototype::public_inputs pushes
the comm VERBATIM from the ContractCall (verify.rs:1946-1948), never
recomputed from FAB inputs — recorded so nobody re-derives the
optimistic version. ≤1% of rows, zero k crossings, a soundness surface
in exchange. Exception worth taking: NARROW checks the port copied
wider than the type (mechanical scan, expect tens of rows).

** Specs: symbolic effect algebra (the key design decision)
Per circuit: fn spec_X(pre: &VaultState, args, wit) -> Outcome where

MapRemove | CellWrite | MintShielded{domain_sep: Term, value} |

** Findings the sweeps pinned (all now tests)
- IDENTITY mpcResponseKey AUTHENTICATES ANYTHING, and =initialize= does
  not reject one. With Q = O, verifying a signature made under d = 0
  recomputes R' = (z/s)G + (r/s)O = (z/s)G, whose x IS r — so it verifies,
  and anyone can produce such a signature knowing no secret. Every settle
  circuit's ONLY authentication gate is then open. =initialize= validates
  =chainId > 0= and =swapRouter != 0= but has no analogous check on
  =responseKey=. Deployer-gated and one-shot, so misconfiguration-class,
  not attacker-reachable — but it is a missing check of exactly the kind
  the contract makes elsewhere. Test asserts the CURRENT behaviour, so
  adding the check will fail the test and force this note to be updated.
- NO COUNTER-OVERFLOW GUARD. At =signetRequestNonce == u64::MAX= every
  circuit assert still passes; it is the Impact VM that refuses (=Addi= →
  =ArithmeticOverflow=). Circuit acceptance and ledger acceptance genuinely
  differ there, and the harness models the split rather than hiding it.
  Needs 2^64 requests; recorded, not actionable.
- FORGED MEMBERSHIP: circuit accepts, ledger refuses. A =member= answer is
  a =Popeq= result, so a prover claiming a pending marker that does not
  exist gets a valid PROOF; only =ResultModeVerify::process_read= catches
  it (=ReadMismatch=). Before this step nothing in the repo executed an op
  stream, so this defence was entirely untested. It is the single best
  argument for the run_program link.
- UNREAD ARGUMENT SLOTS pinned exactly: the attestation's =bigR.y= and
  =recoveryId= always (declared + range-constrained, never consumed —
  faithful to the Compact original), plus the unselected arm of claim's
  =Maybe<Either<..>>= recipient, which varies by shape. Establishing this
  needs the communications commitment RE-DERIVED after the perturbation:
  =comm = transient_commit(inputs, rand)= binds the whole argument vector
  in-circuit, so a naive sweep only re-proves that the commitment binds.
  (On chain it does not: verify.rs:1946-1948 pushes the commitment
  verbatim and never recomputes it — the §"constrain_bits dedup" verdict
  is re-confirmed, not weakened.)
- ECDSA malleability: =s = 0= ABORTS rather than returning false
  ("instruction 49 (inv): cannot invert zero of type Secp256k1Scalar"),
  =r = n= and =s = n= reject, and the classic partner =(r, n − s)= REJECTS
  too. Attestations are therefore not trivially malleable in this
  construction.
- =amount <= u64::MAX= (deposit/withdraw) and the amountOut/amountInMaximum
  equivalents were previously UNREACHABLE by the model, which typed
  amounts as u64. Widened to u128 so generation reaches 2^64 − 1, 2^64 and
  2^128 − 1, per this file's §"Generation strategies".
- completeSwap's =amountInMaximum − amountIn= has six named boundary tests
  (exact spend → 0-coin, cap−1, cap+1, u64::MAX against cap 1, the
  smallest legal cap 1 at spend 0/1/2, and the u64 ceiling). Underflow
  rejects in every direction; the 0-value change coin on an exact spend is
  real and declared.

** Deviation log
Each entry is a deliberate departure from compactc's framing or from the
Compact source's constructions, with the argument that makes it safe. The
executable form of this list is the set of =Art::Opt= arms in
=tests/vault/prims.rs= plus the =fork_status= ledger.

*** D1 (rung i) — one kernel.self() read per circuit
compactc emits a fresh =kernel.self()= read at every stdlib call site that
wants the contract's own address; the optimized vault reads it once and
threads it. The value is the contract's own address, constant for the
whole transaction, and every emitted read still reconciles against the
ledger (=ResultModeVerify::process_read=) — so how many are emitted is
framing, not protocol (§"(b) COMPACTC-FRAMING-ONLY"). In =refund= the two
branches' GUARDED reads become one UNGUARDED read dominating both: the
branches are complementary, so the transcript still carries exactly one
kernel.self answer on either route while the circuit carries one read
instead of two. =claim= and =completeWithdraw= were left alone — the only
removable read in either is inside Compact's own =mintShieldedToken=
auto-receive branch, worth 12 rows in an ECDSA-floored circuit against a
forked copy of a stdlib lowering. The shared helpers gained
"caller already read kernel.self" forms (=receive_shielded_with=,
=burn_coin_with=, =mint_shielded_token_to_key_with=) rather than being
copied; the ports keep the originals and their frozen rows prove the
refactor was inert.

*** D2 (rung ii) — completeSwap's changeNonce is derived, not hashed
=changeNonce = [255 − mintNonce.hi, mintNonce.lo]= replaces
=persistentHash([mintNonce, pad(32, "change")])=. Uniqueness argument:
(a) WITHIN THE CALL the change coin must not collide with the out coin —
both go to the same recipient, so when =tokenIn == tokenOut= and the
change equals =amountOut= the nonce is the only separator, and a collision
would be SILENT (the effects' spend claims are a map keyed by commitment,
so two equal commitments collapse to one entry and a coin is lost).
=255 − hi= has no fixed point over the integers and =mintNonce.hi= is
range-constrained to 8 bits where it is declared, so the two nonces differ
in their top byte for every caller-supplied nonce, unconditionally.
(b) ACROSS CALLS =hi ↦ 255 − hi= is a bijection, so distinct mint nonces
still give distinct change nonces: freshness stays where the port already
put it (the caller's mint nonce), with zswap's global
=CommitmentAlreadyPresent= the same backstop as before.
(c) TOTALITY: =hi ∈ [0,255] ⟹ 255 − hi ∈ [0,255]=, always a canonical
=Bytes<32>=. This file's other candidate, =mintNonce + 1=, is NOT total in
that sense — it can carry the 248-bit low limb out of range.
(d) DISCLOSURE is unchanged: =mintNonce= is a circuit argument both
artifacts publish into the transcript, so the hashed change nonce was
always computable by an observer. The SHA-256 was domain separation
between two public values, not preimage resistance over a secret.

*** D3 (rung iii) — the token domain separator is an encoding
=vaultTokenDomainSeparator(erc20) = 0x01 ‖ 0x00 × 11 ‖ erc20[20]=, i.e.
the slot pair =[hi = 0x01, lo = erc20]=, replacing
=persistentHash([pad(32, "erc20:vault:"), erc20])=. The address limb is
carried VERBATIM, so injectivity is by inspection rather than by
collision resistance; byte 31 is a kind tag ("the vault token of an EVM
ERC-20") that a future token family would change instead of changing the
hash. Safe because the separator is a PRE-TOKEN, not a colour: the ledger
derives the colour itself as
=tokenType(sep, self) = SHA-256([pad(32, "midnight:derive_token"), sep, self])=
(coin-structure/src/contract.rs:58-68, used verify.rs:856-865) and accepts
an arbitrary 32-byte pre-token (§"(c) SPEC-DISCRETIONARY", re-checked at
the pinned rev). Distinct ERC-20s therefore still get distinct colours,
and the contract's own address inside =tokenType= keeps two contracts'
tokens apart even under an identical separator. No new disclosure: the
separator already travels in the clear in
=kernel.mintShielded(domain_sep, value)= and the address is already public
in the stored record. The optimized vault's token colour differs from the
port's — correct, since it is a separate deployment with its own address
and verifier key. A property test asserts the LAYOUT (address verbatim,
zero span, tag byte, equality iff addresses are equal) so the table in the
doc comment and the code cannot drift.

*** Authorisation argument (the deliverable)
Authorisation is =withdrawRefundCommitment(callerSecretKey(), requestId) ==
storedCommitment=, where =storedCommitment= is looked up from the map that
HOLDS the pending marker. The merge keeps that map route-specific:
=stored = cond_select(isWithdrawal, refundCommitment[id],
swapRefundCommitment[id])=, then one =assert(rc == stored)=.
- The route is decided by =refundCommitment.member(id)= ALONE (as in the
  port), and the swap route additionally asserts
  =swapRefundCommitment.member(id)=. An id lives in at most one of the two
  commitment maps (each inserted by exactly one of withdraw/swap, under a
  keccak-derived id that pins the record's kind), so routing is total and
  disjoint.
- On the withdrawal route (=isWithdrawal = 1=) the guarded
  =swapRefundCommitment= lookup emits nothing and its garbage default is
  discarded by the =cond_select=; the gate compares against
  =refundCommitment[id]=, openable only by the original withdrawer's =sk=.
  The swap route is symmetric against =swapRefundCommitment[id]=.
- A WITHDRAWAL-route id can therefore NEVER be settled through the swap
  comparison (it routes =isWithdrawal = 1=, so =stored= is the
  refundCommitment value and the swap map/removes are guarded off), and a
  SWAP-route id can never be settled through the withdrawal comparison. This
  is bit-for-bit the port's authorisation, re-expressed with one shared
  hash. The cross-route traps (=also_other_marker= — id in both maps; id in
  neither; a swap id offered on the withdrawal route) stay green.
