#+title: M17 — Kernel + token stdlib remainder

Design of record for M17, which IS M4's remaining stdlib bullet promoted.
Written before any code, per the milestone. Everything below that is a fact
about compactc or about Midnight's ledger was read off a compiled artifact or
upstream source, and the artifact is named.

The probe is the M17 fixture itself —
=crates/minocrab-contracts/tests/fixtures/kernel/kernel.compact=, 24 circuits
compiled with the PINNED compactc under =--feature-zkir-v3=, one per
operation the milestone names (less the one that cannot be compiled — finding
(a)).

* 0. THE FINDINGS

** (a) =kernel.checkpoint()= CANNOT BE COMPILED for our IR version

M17's first named item does not exist in ZKIR v3. Feeding compactc a contract
that calls it, under the same =--feature-zkir-v3= every other fixture uses:

: unimplemented: [#{vminstr f5kki0ul5pj8zvc19sy1zpm3n-51092} "ckpt" ()]
: Internal error (please report): Exception: failed assertion
: not-implemented at line 748, char 23 of compiler/zkir-v3-passes.ss

The reason is exact and one-sided. The v2 backend assembles it —
[[file:../corpus/src/compact/compiler/zkir-passes/print-zkir.ss][print-zkir.ss:546]] has ~["ckpt" (list (literal 255))]~ — and the v3
backend's =assemble1= has no =ckpt= case at all, so it reaches the
=[else … (assert not-implemented)]= arm
([[file:../corpus/src/compact/compiler/zkir-v3-passes/reduce-to-zkir.ss][reduce-to-zkir.ss:612-615]]).

So =checkpoint= is a v2-only feature, and this is a compactc gap rather than
one of ours. WE COULD emit it — upstream's =Op::Ckpt= is =0xff= and
=ImpactOp::constant= already encodes it — but there would be no artifact to
differential against, and a contract using it could not be written in Compact
for the same target. It is therefore NOT PORTED, and the fairness bullet
should say why rather than list it.

** (b) The milestone's list is TWO LAYERS, and only one of them has vm-code

M17 names fourteen things as if they were one kind. They are not:

| layer | what it is | where |
|---|---|---|
| KERNEL PRIMITIVES | =declare-ledger-adt Kernel= functions with vm-code | midnight-ledger.ss:159-540 |
| STDLIB CIRCUITS | ordinary =export circuit=s written IN COMPACT, composed from the primitives | standard-library.compact:113-350 |

=sendShielded=, =sendUnshielded=, =receiveUnshielded=, =mergeCoin=,
=mergeCoinImmediate=, =unshieldedBalance*= and =blockTimeLt/Lte/Gt/Gte= are
all in the SECOND layer — Compact source, not vm-code. So they are ports of
CIRCUITS (the =minocrab-std= kind of work), and what they compose is the ten
primitives in the first layer.

The ten primitives M17 owes, against the six already ported (=self=,
=mintShielded=, =claimZswapNullifier=, =claimZswapCoinSpend=,
=claimZswapCoinReceive=, =claimContractCall=):

=mintUnshielded=, =claimUnshieldedCoinSpend=, =incUnshieldedOutputs=,
=incUnshieldedInputs=, =balance=, =balanceLessThan=, =balanceGreaterThan=,
=blockTimeLessThan=, =blockTimeGreaterThan= — nine, because =checkpoint= is
finding (a).

** (c) Nine primitives are THREE instruction shapes

This is M16's "two op sequences serve five methods" again, and stronger.

*THE EFFECT ACCUMULATOR* — =mintUnshielded=, =claimUnshieldedCoinSpend=,
=incUnshieldedOutputs=, =incUnshieldedInputs=. All four are the SAME
nineteen-instruction stream (twenty-four for =claimUnshieldedCoinSpend=, and
only because its key is longer). Read off the fixture:

: swap 0                      ; [context, state, effects]
: idxpc [effects slot]        ; 0x80 .. — slot 5/6/7/8, see below
: push (cell KEY)
: dup 1; dup 1; member
: push (cell AMOUNT)
: swap 0; neg; branch 4
:   dup 2; dup 2; idxc [stack]; add
: insc 2
: swap 0

i.e. "map[key] = amount + (map[key] if present else 0)", where the branch
skips the addition when the key is absent. The four differ in exactly three
places: the effects-array slot, the key's type, and the amount's width.

| primitive | slot | key | amount |
|---|---|---|---|
| =mintShielded= (ported) | 4 | =Bytes<32>= | =Uint<64>= |
| =mintUnshielded= | 5 | =Bytes<32>= | =Uint<64>= |
| =incUnshieldedInputs= | 6 | =TokenType= | =Uint<128>= |
| =incUnshieldedOutputs= | 7 | =TokenType= | =Uint<128>= |
| =claimUnshieldedCoinSpend= | 8 | =(TokenType, UnshieldedRecipient)= | =Uint<128>= |

*THE BALANCE READ* — =balance=, =balanceLessThan=, =balanceGreaterThan=.
One shape, "look up the balances map or yield zero", then nothing / =lt= /
=gt=:

: dup 2; idxc [5]            ; the CONTEXT's balances map, not the state's
: dup 0; push (cell KEY); member
: branch 3
:   pop; push (cell 0u128); jmp 1
:   idxc [KEY]
: [push AMOUNT; lt|gt]
: popeqc

*THE BLOCK-TIME READ* — =blockTimeLessThan=, =blockTimeGreaterThan=. Five
instructions, and the two differ ONLY in operand order, which is how a `lt`
becomes a `gt`:

: less than:    dup 2; idxc [2]; push (cell t); lt; popeqc
: greater than: push (cell t); dup 3; idxc [2]; lt; popeqc

** (d) The emission layer already HAS the accumulator — as one special case

The first draft of this note listed =Key::Stack= and =Op::Add= as missing.
They are not: =kernel_mint_shielded= (M4) emits both, because =mintShielded=
IS the effect accumulator of finding (c) at slot 4. So M17's four unshielded
primitives are not new machinery at all — they are the FIFTH through EIGHTH
callers of a shape that has been in the crate since M4 with the slot, the key
and the amount hard-coded into one function.

What M17 does there is generalize that function and give it four more
callers, which is the same move M16 made for the two Merkle-insert streams.
NOTHING in the emission layer is genuinely new for the accumulator; the
balance read and the block-time read are, and they are five and nine
instructions.

This is worth recording because it is the second milestone running whose
"new lowering" turned out to be an existing one with different arguments —
and both times the design note found it before any code was written.

** (e) The v3 corpus covers the SHIELDED half and nothing else

Same filter as M14/M15/M16. Across the three =--feature-zkir-v3= sources the
kernel/token surface used is =kernel.self= (25), =receiveShielded= (10),
=mintShieldedToken= (7), =sendImmediateShielded= (6) — all SHIELDED, and all
already reachable through the ported vault and mint-tokens contracts. NOT ONE
v3 use of any unshielded primitive, of =balance*=, of =blockTime*=, or of
=mergeCoin=.

So the fixture route again, for the fourth milestone running and for the
fourth time with the same recorded reason.

* 2. AS BUILT

** The emission layer, and the shape that was already there

=kernel_mint_shielded= became =kernel_effect_add(slot, key, amount)= with
FIVE callers, per finding (d) — =mintShielded= (4), =mintUnshielded= (5),
=incUnshieldedInputs= (6), =incUnshieldedOutputs= (7),
=claimUnshieldedCoinSpend= (8). Not one instruction of it changed; it grew
three parameters and four callers.

Genuinely new: =kernel_balance= (one emitter, three comparison tails through
a =BalanceCmp=) and =kernel_block_time=. Both carry a detail worth stating,
because it is the same detail twice: compactc has NO =gt= opcode, so
=balanceGreaterThan= and =blockTimeGreaterThan= are the =lt= streams with the
OPERANDS PUSHED IN THE OTHER ORDER — which is why each takes a =greater= flag
that moves a =push= to the front and turns =dup 2= into =dup 3=, rather than
selecting a different opcode.

** The named-immediate gap, closed a third time — and only where it can be

=left<Bytes<32>, Bytes<32>>(color)= is four constant FAB limbs and two wires:
the =is_left= tag and the unused right arm are statically 1, 0, 0. compactc
inlines all four into the Impact =push=; routing them through =LedgerRepr=
names each with a =copy=, and the differential saw it immediately.

M15 recorded exactly this for ledger VALUE positions and left the fix — a
change to =LedgerRepr= that all four vault forks depend on — as dmd's call.
That call is still dmd's and is NOT taken here. What is taken instead is
narrower and needs no trait change: =UnshieldedToken= is its own type,
=left(colour)= is the only =TokenType= Compact's stdlib ever builds, and it
knows its own constants, so it constructs its =LedgerValue= with
=ImpactElem::Imm= directly. The general =Either= =LedgerRepr= impl is
untouched and still wires everything, which is right — a =TokenType= whose
tag is COMPUTED has no constants to inline.

Worth naming as a pattern, since it is now three milestones old: the
named-immediate gap has a general fix (dmd's call, still open) and a series
of local ones, and each local one is legitimate exactly when the constants
belong to the TYPE rather than to a value.

** What is ported, and what is not

PORTED, and byte-equal to compactc up to identifier renaming for all
nineteen: the nine kernel primitives that have vm-code and can be compiled,
and the ten stdlib circuits that are compositions without a conditional —
=blockTimeLt/Gte/Gt/Lte=, =unshieldedBalance{,Lt,Gte,Gt,Lte}=,
=receiveUnshielded=.

NOT PORTED, and each for a stated reason rather than an absence
(=NOT_YET_PORTED= in the differential names them, and
=every_fixture_circuit_is_accounted_for= fails if the list drifts):

- =kernel.checkpoint()= — finding (a). Cannot be compiled for our IR
  version at all. Not a gap of ours.
- =sendShielded=, =mergeCoin=, =mergeCoinImmediate= — the SHIELDED
  compositions, which are much larger (nonce evolution, coin commitments,
  nullifiers, a change-coin branch) and whose pieces already exist in
  ad-hoc form inside the ported vault contracts. Lifting them into the
  stdlib is worth doing and is the natural next stage; it is not started.

** The conditional pair, and the change it forced in a SHARED gadget

=sendUnshielded= and =mintUnshieldedToken= are ported, so 21 of the 24 now
match. Their shared piece is the auto-receive guard,
=recipient.is_left && recipient.left.bytes == kernel.self().bytes=, and two
details of it are compactc's rather than ours: the =kernel.self()= read is
guarded by =is_left= ALONE (a user-address recipient never needs the
contract's address, so the read is skipped and its gates yield the default),
and the conjunction is TWO =cond_select=s rather than a multiplication.

=mintUnshieldedToken= then forced a change outside M17. It calls
=tokenType(domainSep, kernel.self())=, and our =token_type= built its
constant domain prefix with =B32::pad= — two =copy= instructions where
compactc inlines the constants into the =persistent_hash= operand list. That
is the named-immediate gap for a HASH operand, which M16 already built the
mechanism for (=AnyWire3::immediate=); =token_type= was simply the last
stdlib hash operand still naming its constants.

MEASURED MOVEMENT, because =token_type= has ten call sites across all four
vault forks and the benchmark contract is one of them: 26 circuits changed,
and the diff in every one is the SAME TWO =copy= instructions removed plus
renumbering — nothing else.

THE ZERO-ROWS CLAIM IS PROVEN, not assumed. row_snapshot was REGENERATED
after the change and gained exactly TWO lines — the two newly ported
circuits — and lost NONE. So all 26 moved circuits' =(k, rows)= are
identical, which is what "a =copy= of an immediate is zero rows" means and
what M9 phase 7 measured for the same class. Every vault differential still
passes: they compare PI streams, and a removed =copy= does not touch the PI.

So this is a strict improvement — 26 circuits move CLOSER to compactc — but
it is movement, and it is recorded here rather than folded into a
"zero movement" line.

** The shielded compositions, and the four things they needed

=sendShielded=, =mergeCoin= and =mergeCoinImmediate= are ported, so ALL 24 of
the fixture's circuits now match compactc instruction for instruction and
=NOT_YET_PORTED= is empty.

They are the only circuits here with coin ALGEBRA between the kernel calls —
a nonce derived, a commitment hashed, a value split into what is sent and
what comes back — and four small things had to exist first. Each is a
primitive that compactc's own lowering has and ours did not:

1. =Circuit3::copy=. A =Copy= is a rename and zero rows, but compactc emits
   one for every CAST: =(a.value + b.value) as Uint<128>= names its
   range-checked result, and =degradeToTransient(nonce)= names the limb it
   degrades. Without it a port cannot BE compactc's lowering, only agree with
   it up to a missing instruction.
2. =transient_hash= over =AnyWire3=. Poseidon's operand list had accepted
   wires only, so a constant domain separator had to be named first. It now
   takes the same operand type =persistent_hash= has taken since M16, and the
   nonce-evolution tag is inline. This is the named-immediate gap AGAIN — the
   fourth appearance, and the first in the transient flavor.
3. =degrade_to_transient= / =upgrade_from_transient= for v3. The v2 twins have
   existed since M4; the v3 ones are the same rule with compactc's shape —
   the degrade IS the =Copy= of (1), and the upgrade emits its zero high limb
   BEFORE the =div_mod=, because that is the order in the artifact.
4. =coin_commitment_to= and =coin_commitment_to_contract=. See below.

*** The recipient select, hoisted and folded

=coinCommitment= takes a recipient and hashes ONE address, so it selects
between the =Either='s two arms. Two things about that select are compactc's
and were not ours:

- A recipient that is a static =right(addr)= — every coin a contract pays
  ITSELF, which is `receiveShielded`, `mergeCoin`'s output and
  `sendShielded`'s change coin — has NOTHING to select. compactc inlines the
  tag as the immediate =0x00= and hashes the address directly.
  =coin_commitment_to_contract= is that, and it is a distinct function rather
  than a fold inside the general one for the reason M17 stage 3 gave for
  =UnshieldedToken=: the constants belong to the CONSTRUCTOR, not to a value.
- A circuit that commits to the same coin TWICE — =sendShielded= claims the
  spend and then, on the self-send path, the receive — selects once and
  hashes twice. compactc CSEs the =cond_select= pair and does not CSE the
  =persistent_hash=. So the select is hoisted to the caller and
  =coin_commitment_to= takes the tag and the address it produced.

*** What the value branch taught, and why it is written out

=sendShielded= ends in Compact's =if= as an EXPRESSION — =change == 0= gives
=none=, otherwise =some(changeCoin)= — which is exactly what this session's
=when_value= chain is for. It is NOT used, and the reason is worth recording
because it is a limit of the abstraction rather than an oversight:

compactc FOLDS the =Maybe='s tag into the guard it already has. =none= and
=some= differ in a tag that is 0 on one side and 1 on the other, so selecting
it is =cond_select(change == 0, 0, 1)= — which is bit-for-bit the =else= arm's
guard, already computed and already named. A chain would emit that select a
SECOND time (one instruction, zero rows, but a visible difference). So the
port names the guard once and uses it as the tag, and selects only the five
payload slots. The effects still go through =c.when=, which is byte-identical
to the hand-threaded form.

Same story one level down, and the same conclusion: our =&&= is
=predicate::and=, which is a =mul=; compactc's is a =cond_select=. Both are
correct on booleans and cost the same, but a circuit that must match
instruction for instruction cannot go through the predicate vocabulary for a
conjunction. =bytes_eq= writes compactc's shape once, and =is_self= (stage 3)
already had it.

BOTH are arguments for the normalisation pass notes/ir-passes.org §2(ii)
describes, from a direction that note did not anticipate: the surface API can
only be as ergonomic as the LOWERING lets it be, as long as the bar is
instruction equality with compactc. A pass that folded =cond_select(b, 0, 1)=
and CSEd pure instructions would let both of these be written the obvious way.

*** MEASURED MOVEMENT, and it is the same class as stage 3's

Inlining the two constants in =coin_nullifier_contract= and =coin_commitment=
(the domain prefixes and the nullifier's =dataType= byte) moved 28
PRE-EXISTING circuits: six vault circuits in each of the four forks, both
mint-tokens circuits, and xcall-with-payment's notify and pay. 42 =copy=
instructions removed in total, between one and four per circuit.

The claim that nothing else changed is CHECKED, not asserted: every one of the
28 dumps was compared against its baseline after substituting each removed
=copy='s immediate for its output name, and all 28 are then IDENTICAL. And
row_snapshot was regenerated: +3 lines for the new circuits, ZERO deletions,
so no =(k, rows)= moved anywhere. Every differential still passes, because a
removed =copy= does not touch the PI stream.

28 more circuits move CLOSER to compactc, and the benchmark contract is among
them — recorded as movement rather than folded into a zero-movement line.

*** NOT DONE, and named

The vault's own shielded compositions in =minocrab_contracts::common= —
=receive_shielded=, =burn_coin=, =mint_shielded_token= — are ad-hoc twins of
what now exists in the stdlib. Lifting them is worth doing and is not in this
commit, because unlike the =copy= change it would MOVE ROWS: every static
=right(kernel.self())= recipient would drop two =cond_select=s.

THE TWO CLASSES, measured rather than assumed (=minocrab-sim/examples/opcost.rs=,
new cases): 100 =copy=s of an immediate cost ZERO rows (64 → 64), and 100
=cond_select=s cost 101 (64 → 165) — so a select is one row and a rename is
none. That is why this session's 42 removed =copy=s left row_snapshot
bit-identical, and why the lifting would not: ~2 rows per site, which crosses
no =k= boundary and changes no prove time, but does move a frozen instrument
and therefore has to be a deliberate change with its own gate rather than a
refactor slipped in beside a port. Queued in notes/review-queue.org.
