#+TITLE: ZKIR op costs under Midnight's cost model, and what they bought on the passport port
#+DATE: 2026-10-15

Measured 2026-10-15 with =minocrab_sim::v3::cost= (Midnight's own =IrSource::model()=, the k and row count the prover will see) on one-op circuits, baseline (empty circuit) subtracted. Backend: midnight-ledger 04c9c5d's zkir-v3, the one main is pinned to; the passport PR #184 numbers it reproduces were produced on midnight-zkir 3.1.0-rc.1, and every one of the 52 circuits came out identical to the row, so the two models agree on these ops. The table is the thing to have open when a circuit is 2k rows over a power of two.

* 2. What the table said about the passport port, and what was lifted into std

The port (passport PR #184, machine-written, 52 circuits) built against this branch's crates reproduces the PR's k and rows exactly. Its op histograms against the table:

- *P-256 circuits spent ~50k of 124k rows on byte extraction*: 342 =div_mod_power_of_two= per circuit — 256 of them one-bit splits for base64 (the Compact reference's =byte_bits= does the same with 8 comparisons and 7 selects per byte, and compactc's own byte indexing adds 292 splits), 36 to get three bytes out of a 37-byte =authenticator_data=, 21 for the origin check. The fix is arithmetic, no new witnesses: recombine each 3-byte group big-endian and split it three times by six bits (62 splits for the whole encoding), and split only the 6-byte leftover limb of the authenticator data (5 splits). Lifted as =v3::base64url_32= — 40.8k rows less per P-256 circuit.
- *Every challenge-bearing circuit hashed a constant 64-byte domain tag in-circuit*: 3,750 rows. compactc does not constant-fold =persistentHash=. Lifted as =hash::Preimage= (the port's builder, with =uint= taking a typed =Uint<BITS>= so a hash limb cannot be wider than its slot) whose =hash= folds an all-immediate preimage off-circuit via =hash::constant_persistent_hash=, checked against the chip by simulation.
- *The JubJub small-order check was two scalar multiplications*: =ecMul(pk, 8) != ecMulGenerator(0)= is 402 + 688 + 402 + 688 + 15 ≈ 2.2k rows for a cofactor test. Three doublings and a coordinate compare are ~30. Lifted as =JubjubPoint::times_cofactor= / =is_identity= / =assert_not_small_order=; =times_cofactor= is checked equal to =ec_mul(p, 8)= by simulation on five points (the twisted-Edwards addition law is complete, so =add(p, p)= is doubling).
- *=kernel.caller= did not exist*, so the port hand-assembled thirteen Impact ops. Lifted as =kernel::caller= (=minocrab_ledger::kernel_caller=), byte-for-byte compactc 0.35.0's lowering, asserted by a test against the artifact's opcodes.
- Smaller: =B32::eq= (the port's =bytes_eq=, eleven uses), =Check::implies= (one select where =not(a).or(b)= is four instructions), =LedgerCell<Uint<N>>::add= (the port's hand-written =increment=), and the executor's FAB-atom normalisation (a real bug the port's fork fixed: an absent union arm must decode as the ledger's canonical empty atom) with its two regression tests.
- NOT lifted here: =GeneratorScalarTy for Secp256r1ScalarT= — the backend main is pinned to (04c9c5d) has no P-256 generator arm; that belongs with the zkir-3.1 bump.

* 3. The measured effect on the port

The port's scratch copy with the std helpers substituted (tags as immediates, =assert_not_small_order=, =base64url_32=, the limb-aware authenticator split, =when(..).otherwise(..)= in =deposit_unshielded=, =kernel::caller=), through the same cost model:

| | before | after |
|---+--------+-------|
| total rows, 52 circuits | 3,656,014 | 2,948,966 (−19.3%) |
| k lowered | — | 14 of 52 circuits |
| P-256 circuits at k=18 | 9 | 0 (all nine → 17) |
| JubJub k changes | — | append_inbox 16→15, remove_device 16→15, publish_recovery_session 16→15, withdraw_shielded_with_grant 17→16, withdraw_shielded_to_contract_with_grant 17→16, recover_finalise 12→11 |
| per P-256 circuit | | −34.4k to −40.8k rows |
| per JubJub device circuit | | −5.05k rows (tag fold 3.75k + cofactor check 1.3k) |
| per k256 device circuit | | −3.75k rows (the tag fold; the ECDSA floor is 23.4k) |

The k=17 → 16 that would matter most for k256 (=withdraw_shielded_with_k256=, 67.7k → 64.0k) did not happen: 2^16 is 65,536 and the backend's reserved rows put the real threshold near 61-62k, so another ~2.5k has to come from the protocol-fixed parts (nine SHA blocks and the ECDSA), which is to say from Compact-side spec changes (a 32-byte tag where 8 would do, preimages packed to block boundaries), not from the eDSL.

Soundness notes for the three big ones: the fold is SHA-256 over the same FAB binary encoding the chip hashes (=ValueReprAlignedValue::binary_repr=) and the test holds the two equal; base64url is exact integer arithmetic on byte values the circuit already range-checked (the 24-bit group is below the field, the splits are the backend's); the cofactor doubling relies on completeness of the JubJub addition law, true for twisted Edwards with non-square =d= and asserted by simulation — a real proof of =times_cofactor= against the backend's gadget is the remaining check before anyone relies on it for a stored key.

Unchanged and still pinned identical: =block_time_lt= / =_gt=, =unshielded_balance= / =_lt= / =_gt=, =receive_unshielded=, =secp256k1_ecdsa_verify=.

THE EQUIVALENCE, per change, and what still constrains each value a replaced instruction used to constrain (a =cond_select= makes its selector a bit, =not= its operand):
- =not(b)= as =not= instead of =cond_select(b, 0, 1)=: the same bit check on =b= (=ir_vm.rs:1186-1193= against =:1064-1071=) and the same value =1 - b=.
- =a && b= on two =test_eq= outputs as =mul=: both are bits by construction (=is_equal='s output), so the selector check dropped was on a bit already.
- =is_self='s outer =cond_select(is_left, both, 0)= KEPT: it is the only instruction that constrains =is_left= to a bit when no read is emitted (the kept address). A mutation to =mul(is_left, both)= is caught by =agree_send_unshielded= (=is_left = 2= under an off guard is accepted).
- =send_shielded='s =cond_select(is_left, 0, same)= KEPT for the same reason.
- The explicit guard in one =when= scope instead of per op: the scope's guard is =cond_select(ambient, g, 0)= computed once (=effects.rs:128-134=), per op it is the same instruction repeated (=:102-106=), so every Impact op carries the same guard value.
- One coin commitment instead of two: the same =persistent_hash= over the same wires.
- =as_uint128= without the =copy=: an alias.

What executes them: NOTHING in the workspace calls std's token circuits (every port uses compat's copies, and the three MinoCrab-only modules call none of them), so the only execution of the lean forms is =same_as_std.rs=: each case on the on-chain VM through =minocrab_sim::v3::exec= at top level and under a =when=, under =EveryCall= against the whole preimage (transcript in and out, public inputs, skips, outputs, effects, post-state, upstream =check=) and under the default =OncePerCircuit= against verdict, outputs, effects and post-state (the lean side may read =kernel.self()= less). Cases: recipient self, another contract, a contract sharing one limb with self, a user, and a tag of 2 (refused); amounts 0, 7, 2^64-1; two colours; for the merges same and different colour (refused) and a sum past =Uint<128>= (refused); for =send_shielded= spending all, part, nothing of a zero coin, more than the coin holds (refused) and a coin holding 2^128-1. No input on which the lean and compactc-shaped forms disagreed was found.

* 5. OPEN: the identity check in =secp256k1EcdsaVerify=, for dmd to take upstream or decide (2026-11-21)

Not changed: std's and compat's =secp256k1_ecdsa_verify= are the same code and stay so. compactc 0.36 refuses the identity key with =test_eq(pk, ec_mul_generator(from_bytes32(into_bytes32(0))))=, then =not=, then =assert= (=crates/minocrab-compat/src/secp.rs=, =assert_not_identity=): about 12,300 rows, almost all of them the =ec_mul_generator= of a constant zero. The cheaper candidate is one =into_coordinates(pk)= (44 rows), whose in-circuit arm asserts the point is not the identity. The question is whether the two refuse exactly the same witnesses. Read in the cargo registry sources the workspace builds (midnight-zkir 3.2.0, midnight-circuits 7.3.0):

- ESTABLISHED, =into_coordinates= refuses exactly =is_id = 1=: =ir_instructions/into_coordinates.rs:105-111= (zkir) maps a =Secp256k1Point= to =secp256k1().x(..)= and =.y(..)=; =ecc/foreign/weierstrass_chip.rs:967= (=x=) and =:976= (=y=) call =assert_non_zero=, which is =assert_equal_to_fixed(is_id, false)= (=:646-652=). Off circuit the instruction errors on the identity (=into_coordinates.rs:46-50=), so an honest prover cannot even build the preimage.
- ESTABLISHED, a witness point CAN carry the identity flag with arbitrary coordinates: a =Secp256k1Point= circuit input is assigned by =assign_incircuit= (=ir_instructions/assign.rs:100-103=, whose =assign_many= is the trait default, one =assign= per value (=instructions/assignments.rs:87-96=)) through the chip's =assign= (=weierstrass_chip.rs:343-359=; secp256k1 has cofactor 1, so =assign_without_subgroup_check=, =:936-952=), which is =assign_point_unchecked= (=:1101-1125=: =x=, =y= and the bit =is_id= are three free witnesses) plus =assert_is_on_curve= CONDITIONAL on =not(is_id)=. The type's own doc says so (=:176-178=: "If =is_id= is set, the values of =x= and =y= are irrelevant and can be anything").
- ESTABLISHED, point =test_eq= ignores the coordinates of two identities: =ir_instructions/eq.rs:120= is the chip's =is_equal= (=weierstrass_chip.rs:570-588=), =(p.is_id == q.is_id) && ((x and y equal) || (p.is_id && q.is_id))=. So IF =q.is_id = 1=, =test_eq(pk, q) = pk.is_id= for every witness, whatever its coordinates, and compactc's assert refuses exactly =pk.is_id = 1=: the same set =into_coordinates= refuses.
- NOT ESTABLISHED: that =ec_mul_generator= of the constant zero has =is_id = 1= in EVERY satisfying assignment. Its in-circuit arm (=ir_vm.rs:1310-1320=) is =assign_fixed(generator)= followed by the general =ec_mul_incircuit= (=ir_instructions/ec_mul.rs:70-76=), i.e. the chip's =msm= (=weierstrass_chip.rs:788= onwards, with randomised accumulation, =msm_randomness= at =:1735=), whose result point is assigned by the prover and tied down by the gadget's addition constraints. The complete =add= ties =r.is_id= exactly to =p = -q= (=:733-734=), which suggests the result flag is determined, but the msm was not read through. If it were NOT determined, compactc's check would be WEAKER than =into_coordinates= (a prover choosing =is_id = 0= for =G·0= with coordinates differing from the key's would make =test_eq= false for a key with =is_id = 1=), so the cheaper form can only refuse more, never less.

What follows: replacing the check with =into_coordinates(pk)= is sound in the direction that matters (it refuses every identity witness, by an unconditional assertion) and refuses at least what compactc's refuses; it refuses exactly the same set iff the open point holds. It is also a different stream, so it is only for a MinoCrab-only circuit, and none of the three calls this verify today. The upstream question to ask: is =ec_mul= / =ec_mul_generator= with a zero scalar guaranteed to yield =is_id = 1= (and should Compact's library compare with the identity through =is_zero= rather than build it)?
