#+title: M37 — Typed EVM calls: the call as a type, the slot infers the rest

* 0. The ask (dmd, 2026-09-05)
"Higher level constructs that make the ERC-20 transfer more terse and easy
to read … more type safety … more inference" — then, against a first
sketch that parsed a Solidity signature string in an attribute macro: "I'd
rather that we have a type somewhere in our system that represents the
input and output, e.g. a tuple and a bool, then that request type is
inferred. I'm also keen for macros that don't completely break tooling."
And on the selector: "Do we actually need a const fn Keccak? Why not just
run it when we run the eDSL?" — we don't; circuit construction is Rust at
build time, so the selector is hashed there with =sha3= and embedded as
an immediate. In-circuit hashing stays Poseidon throughout; no artifact
gains a =keccak256= instruction.

THE TARGET SHAPE (the README's cross-chain example, as real code):
#+begin_src rust
pub struct Erc20Transfer;
impl EvmCall for Erc20Transfer {
    const NAME: &'static str = "transfer";
    type Args = (Address, U64);       // `address`, `uint256` narrowed to 64 bits
    type Return = Bool;               // the attested output
    const KIND: u8 = 7;               // the protocol byte — explicit, a wire commitment
    const GAS_LIMIT: u64 = 100_000;   // the limit, not a price (fees are the envelope's)
}

#[derive(Ledger)]
pub struct Treasury {
    pub signet: Signet,
    pub transfers: Pending<Erc20Transfer, Owned<Amount>, 2>,
}

#[circuit]
pub fn send(c: &mut Circuit3, token: Contract<Erc20>, to: EvmAddress, amount: Uint<64>)
    -> Discloses<(SentAmount,)>
{
    let amount = amount.disclose_as::<SentAmount>(c);
    TREASURY.transfers.request(c, token, (to, amount), Amount(amount));
}

#[circuit]
pub fn complete(c: &mut Circuit3, ticket: Succeeded<Erc20Transfer>) -> Discloses<(Transferred,)> {
    TREASURY.transfers.complete(c, ticket).output.disclose_as::<Transferred>(c);
}

#[circuit]
pub fn refund(c: &mut Circuit3, ticket: Failed<Erc20Transfer>) -> Discloses<(RefundRecipient,)> {
    let (owner, Amount(amount)) = TREASURY.transfers.refund_to_owner(c, ticket);
    // ... re-mint `amount` to `owner`
}
#+end_src
Anyone may =complete= (the attestation is the gate); only the original
caller may =refund= (the owner commitment is opened with a fresh witness).

* 1. The ABI type layer — types, no macro
=trait AbiType= (crates/minocrab-contracts/src/evm.rs, new):
- =const SOLIDITY: &'static str= — the spelling in the selector
  signature: ="address"=, ="bool"=, ="bytes32"=, ="uint256"= (for U64,
  U128 and U256 alike: the ABI word is always 32 bytes; the Rust type
  states the RANGE the contract accepts).
- =const RESPOND: &'static str= — the attested-output schema spelling
  the record carries (="uint64"= for U64, ="bool"= …), i.e. the
  narrowing the MPC applies (=SUPPLY_RESPOND_SCHEMA= today).
- =type Wire<V: Vis3>= — the circuit value: =Address::Wire = EvmAddress<V>=,
  =U64::Wire = Uint<64, V>=, =U128::Wire = Uint<128, V>=, =U256::Wire =
  Bytes<32, V>=, =Bool::Wire = Bool<V>=, =Bytes32::Wire = Bytes<32, V>=.
- =fn word(c, &Wire<V>) -> B32<V>= — the encoder: the EXISTING
  =signet::evm_address_abi_word= / =numeric_abi_word= moved under the
  trait unchanged (zero movement).
=trait AbiTuple= for =()=, =(A,)= … eight-tuples: =const WORDS: usize=,
=const SIGNATURE: &'static str= (comma-joined SOLIDITY spellings — a
=const= string built by a small const concatenation or, simpler, a
=fn signature() -> String= evaluated at build time; the selector is
built at build time anyway), =type Wires<V>= (the tuple of =Wire=s),
=fn words(c, Wires<V>) -> Vec<B32<V>>= (length == WORDS, checked into the
record's fixed array at the slot).

* 2. =EvmCall= — the call as a type
#+begin_src rust
pub trait EvmCall {
    const NAME: &'static str;
    type Args: AbiTuple;
    type Return: AbiType;        // Attested<Return::Wire> is the Response; KIND below
    const KIND: u8;
    const GAS_LIMIT: u64;
    fn selector() -> [u8; 4] { keccak256(format!("{NAME}({Args::SIGNATURE})"))[..4] }  // build time, sha3
}
#+end_src
=Attested<R>= gains =impl<C: EvmCall> Response for Attested<C::Return>=
… (the KIND comes from the call, so the response type is not written).
The FIXTURE: the selector and words of =Erc20Transfer=, =Erc20Approve=,
=ExactOutputSingle=, =Erc4626Deposit=, =Erc4626Redeem= pinned against
compactc's own calldata — the vault differential's transcripts already
carry every word; a test asserts our encoder's words equal them and the
selector equals the first four calldata bytes. Not a hash test in a
circuit.

* 3. =Pending<Call, Env, WORDS>= — the slot infers the rest
- =Resp= is gone (=Attested<Call::Return>= at =Call::KIND=). =KINDS=
  uniqueness across a block is ALREADY asserted by the Ledger derive
  (ledger.rs "No two slots of one block settle under the same Signet
  response") — keep, cite.
- WORDS: stable Rust cannot write =EventRecordV2<{ Call::Args::WORDS }>=
  (=generic_const_exprs=). DECISION: WORDS stays a const generic on the
  slot, CHECKED — an inline const assert =WORDS == <Call::Args as
  AbiTuple>::WORDS= makes a mismatch a compile error. Inference of that
  one number waits for =generic_const_exprs= or a =generic-array=
  rewrite of =EventRecordV2= (recorded, not done: it re-types every
  record user for one integer).
- The =Signet= block is found by the Ledger derive: exactly one =Signet=
  field per block (zero or two: a compile error from the derive), and
  every =Pending= slot is constructed with the Signet's block offset
  (=Pending::at_block_with_signet(total, start, signet_start)=), so
  =request= / =complete= / =refund= take no =&VAULT.signet=.
- =request(c, callee: Contract<Abi>, args: <Args as AbiTuple>::Wires<Private>,
  env)= builds the =EvmTx= (selector, words, GAS_LIMIT, the fixed fee
  envelope, the contract's own signing path, the Signet's key version)
  and files it; =Contract<Abi>= is a newtype over =EvmAddress= so a
  callee and a recipient cannot swap. The per-circuit =evm_nonce=
  argument stays an input for now (the nonce/admin-gas conversation is
  next — §7).
- Tickets, SYMMETRIC (dmd): =Succeeded<Call>= and =Failed<Call>=.
  =complete(c, Succeeded<Call>)= asserts =kind == Call::KIND= AND
  =Return::is_success(output)= (=AbiReturn::is_success=: a =Bool= return
  is its own value; a numeric return is =true= — executed is success);
  =refund(c, Failed<Call>)= accepts =kind == FAILURE= OR =kind ==
  Call::KIND && !is_success(output)=. WHY (dmd's question, 2026-09-05:
  "is false, but succeeding a failure … would that lead to a spurious
  completion?"): yes — an ERC-20 =transfer= can mine and return =false=;
  an API whose =complete= accepted any executed attestation would let a
  contract mark done a transfer that moved nothing, with the MPC's
  failure kind (= never executed) unavailable. The deployed vault avoids
  it with the refund branch INSIDE =completeWithdraw= — the origin of
  Gap 2. Here the two non-successes are one owner-only ticket and a
  =false= cannot complete, whoever presents it. Cost: nil — the failure
  payload and the executed-bool payload are each one limb, so digest,
  signature and lookup are shared and the outcome is a kind disjunction.
  =Requested= / =Settled= labels are the slot's.

** 3.2 The outcome rule as a FUNCTION (dmd, 2026-09-06: "I don't really
like the outcome flag, I want a function that takes the successful
response and runs a predicate on it")
The marker-type design (=OutcomeRule= with =Always= / =ByFlag= /
=ByPredicate=) carried two ideas — the predicate and a payload shaping —
and the second was not asked for. Workshopped four function forms:
- D1 one defaulted =succeeded= on =EvmCall=, default "executed is
  success": least boilerplate, but a =Bool=-returning call whose author
  forgets the override silently treats =false= as success — the hole
  reopens.
- D2 the same method, no default: nothing forgotten; one boilerplate
  line (=always=) on every trivial call.
- D3 the default derived from the RETURN TYPE (=AbiType::success=:
  =Bool= → =is_true=, numeric and =Unit= → =always=), =EvmCall::
  succeeded= defaults to it and may override with a domain predicate
  (=shares.gt(0)=): the safe rule is what the wire type says, so a
  =Bool= cannot be silently treated as success even when nothing is
  written; the no-return token is =Return = Unit=. RECOMMENDED and
  built provisionally.
- D4 filter + map (=type Success= + =map=): payload shaping on top;
  deferred until a call needs a real projection.
Common to all: the predicate is a =Check= (composes, carries a message,
costs nothing until asserted); =complete= asserts it, =refund= asserts
=kind == FAILURE || !succeeded=; the trivial rule is free by the
=assert(imm 1)= fold (=passes::drop_true_asserts=, 3c17586, run-equality
proven in =AssertIr.lean=). D3 → D2 is deleting the default: dmd's call.

** 3.1 HAZARD — what the MPC's failure output actually means, and USDT
mpc's execution watcher (chain-signatures/chain-ethereum/src/
execution_watcher.rs, =execution_confirmed_event=): a MINED receipt with
=status = success= has its return data decoded into the request's output
schema and attested; a reverted receipt, OR a terminal decode failure,
resolves the request as =ExecutionOutcome::Failed= — the fixed failure
output. So "never executed" (as this note and the vault harness say) is
too narrow: the failure kind means "reverted, never mined, or output
undecodable". Three cases for an ERC-20 =transfer=:
1. reverted → =Failed= → refund. Covered.
2. mined, returned =false= → attested executed with =ok = false= → the
   spurious-completion hole; =Succeeded= asserting =is_success= closes it.
3. mined, returned NOTHING (USDT, BNB and other non-conforming tokens omit
   the =bool=) → decoding a =bool= from empty return data is a terminal
   extraction failure → attested =Failed= for a transfer that MOVED the
   tokens → a SPURIOUS REFUND on our side: the owner is refunded and the
   recipient keeps the tokens. Neither ticket type can see this from the
   attestation alone. This is the more dangerous direction.
CONSEQUENCE: success is a property of the CALL TYPE, not of the return
value's presence. Options, in order: (i) per-token declaration — the
callee's registration says whether it returns =Bool= or =()= (a
=Contract<Erc20>= vs =Contract<Erc20NoReturn>= marker, chosen when the
address is configured, so =Erc20Transfer= is instantiated per callee
kind); (ii) success from the =Transfer= event or a balance delta, which
the MPC would have to extract (a protocol change on sig-net's side).
Until (i) or (ii) lands, a treasury needs a token allow-list — the vault
has one in effect through its configured ERC-20 addresses — and the note
says so where the API is documented. Rough mainnet base rates (from
memory, not measured): reverts are a few percent of all transactions and
10%+ under congestion; DEX swaps fail far more often than transfers;
returned-=false= tokens are rare and mostly old; no-return tokens include
the largest stablecoin.

* 4. =Owned<Env>= — "only the original caller"
=Owned<E> { owner: Commit<SecretKey, RefundTag>, inner: E }=; =request=
witnesses the secret, commits it bound to the request id and stores it;
=refund_to_owner(c, Failed<Call>) -> (ZswapCoinPublicKey, E)= witnesses a
fresh secret, opens the commitment, returns the owner's public key and the
env; =complete= has no method that consumes a secret — the deployed
vault's Gap 2 is unwritable on this API. =Commit<T, Tag>= takes its domain
tag as a TYPE (a =DisclosureLabel=-style marker with the pad string), so
=to= and =open= cannot disagree (a type error where today it is a proof
that never verifies).

* 5. What stays explicit, on purpose
The kind byte; the labels the author adds (=SentAmount=, =Transferred=);
the guards; the =Discloses= tuple (the declaration is the point; the
generated set-equality test keeps it honest). What the reader no longer
writes: selector, words, word count (checked), response type, schema
strings, gas envelope, the Signet reference, the signing path, the key
version, the owner commitment's construction and opening.

* 6. Tooling
No new macro. The Ledger derive is extended (Signet offset into each
slot); derives leave the annotated item intact. The two attribute macros
that rewrite items (=#[circuit]=, =#[contract]=) are audited as a
separate item: each must keep the author's fn textually intact and add
siblings only, so rust-analyzer's goto/hover/rename work inside bodies —
stated as a property with a test on the expansion.

** Four adjustments the design of record needed
1. =EvmCall::signature()= IS A METHOD, not just =NAME= + =Args::SIGNATURE=.
   Uniswap's argument list is a Solidity STRUCT, which the ABI renders as a
   nested tuple: =exactOutputSingle((address,…))=, two pairs of
   parentheses. §2's default cannot spell that, so =signature()= is
   defaulted-and-overridable and =ExactOutputSingle= is the one override
   (three lines). A test asserts the flat spelling hashes to something
   ELSE, so the wrapping is not decoration.
   Also: §1 says =const SIGNATURE: &'static str= "or, simpler, a fn". It is
   the fn. A const would need const string concatenation, which on stable
   needs =generic_const_exprs= for the length — the same wall as §3, and
   for the same one integer.
2. TWO ABI TYPES §1 DOES NOT LIST, because the corpus uses them: =U24=
   (Uniswap's fee tier, =SwapRequest::fee: Uint<24>=) and =U160=
   (=sqrtPriceLimitX96=). Both are needed for the seven-word signature to
   hash correctly — the selector is over =uint24= and =uint160=, not
   =uint256=.
3. =Erc20Transfer::Args= IS =(Address, U128)=, NOT §0's =(Address, U64)=.
   The deployed vault's amounts enter as =Uint<128>=
   (=DepositRequest::amount=, =WithdrawRequest::amount=,
   =SwapRequest::amountOut=). =Uint<64> -> Uint<128>= is =.widen()=, free,
   no instruction; the other direction is a range check. Taking the wider
   type is therefore the choice that lets rung D re-express the vault
   without emitting a constraint the vault does not emit today, and the
   README's =Uint<64>= caller pays nothing to reach it. The SOLIDITY
   spelling is =uint256= either way, so no selector moves.
   For the same reason =Erc20Approve::Args= is =(Address, U256)=: the vault
   passes =unlimited_allowance_word=, a constant =B32=, through no encoder
   at all — and =U256='s wire IS the pre-encoded word.
4. =U160= and =U256= carry an ALREADY-ENCODED =B32= rather than a
   =Uint<160>= / a decomposition. Nothing in a 255-bit field holds 256
   bits, and the corpus's two full-width values (the unlimited allowance,
   the zero price limit) are both built as constant words. The identity
   encoder emits nothing, which is what the vault emits today.

** One thing rung D will have to decide (found, not fixed)
A call type carries exactly ONE =KIND=, and the vault files
=transfer(address,uint256)= under TWO: =RESPONSE_KIND_CLAIM= (0) for a
deposit and =RESPONSE_KIND_WITHDRAW= (1) for a withdrawal. =Erc20Transfer=
here takes WITHDRAW; the deposit slot needs a second unit type with the
same =NAME= and =Args= and =KIND = RESPONSE_KIND_CLAIM=. That is three
lines and it is arguably RIGHT — the two are different operations of the
protocol and the kind byte is what says so (§5: "the kind byte … stays
explicit, on purpose") — but it is a shape §2 does not mention.
Second, smaller: =deposit= supplies a CALLER-CHOSEN gas envelope
(=max_priority_fee_per_gas= and =max_fee_per_gas= are circuit arguments),
where every other request uses the contract-fixed one. =build_tx= fixes
the envelope, so either =deposit= changes or =build_tx= grows an envelope
argument — which is §7's conversation (an administrator-set gas price)
arriving early.

** What =Failed<Call>= costs — §3's "cost: nil" was WRONG, and why
§3 said "the failure payload and the executed-bool payload are each one
limb, so digest, signature and lookup are shared". They are not. Per
spec/borsh-subset.md §5 the MPC's failure output is
=FailureResponse { kind: u8 }= — ONE byte, the kind itself, no payload —
where an executed =transfer='s is =VaultResponse { kind, success }=, two.
The signed preimages are therefore Poseidon over THREE and FOUR field
elements, and Poseidon is not a stream: one hash cannot cover both.
=Pending::refund= hashes the preimage both ways, selects the field
element by the kind byte with a =cond_select=, and then upgrades and
verifies ONCE. Measured: the second digest plus the select is 46 rows
(a 3-limb =transient_hash= alone is 45). =refund= as a whole is 398 rows
above =complete= (1.6%) at the same k=15 — the 46, plus the kind
disjunction, the owner commitment's opening and =own_public_key=. The
ECDSA verification the two share is ~25,000.

** Six places the design of record needed adjusting
1. §3.2's marker types are GONE (dmd, 2026-09-06, twice: first "a
   function that takes the successful response and runs a predicate",
   then D3 → D2 — delete the =AbiType::success= default too). Final
   form is D2 + D4: a required =succeeded= plus a =Success= mapping with
   an identity default. Recorded above.
2. VISIBILITY. dmd's sketch spells =Wire<Public>= / =Check<Public>=.
   The attested output arrives on a ticket, and a ticket is a
   =CircuitArg=, so its wires are =Private= by construction — there is no
   =Wire<Public>= to take. Built at =Private= throughout. Disclosing the
   attested value inside =complete= would need a label, which belongs to
   the contract, not the slot; the treasury discloses what it wants
   after the fact, as the vault's settle circuits do.
3. =Unit='s =word= is a build-time PANIC, where the hard rule prefers a
   compile error. Making it one needs =Args= and =Return= to be
   different traits (=AbiTuple= is over =AbiType=, so a =Unit= in an
   argument list type-checks today and would file a silent zero word).
   The panic carries a prescriptive message. RECORDED FOR DMD.
   Second, smaller: =()= is not a =CircuitArg= or a =CircuitBorsh= in
   minocrab-std, so a =Pending= over a =Unit=-return call cannot form a
   ticket yet. Adding those two impls is a screenful in
   =minocrab-std/src/v3/entry.rs= and =borsh.rs=; not done here, because
   nothing in the corpus files a no-return call and the brief's slot work
   is over =Erc20Transfer=.
4. THE SIGNING PATH is the contract's constant, and the slot has no way
   to hear it: =SigningPath::contract_path(c)= is =pad(32, "vault")= for
   every lineage in this workspace, so the generalisation here is the
   NAME. A per-contract pad wants the same home as the nonce and the gas
   policy — §7.
5. =Commit<T, Tag>= is ADDED BESIDE =signet_flow::Commit=, not
   substituted for it. Migrating the vault's five call sites is
   mechanical and byte-identical (the pad is the same string), but it is
   an edit to circuits rung D owns, and the brief says those stay
   unchanged until D.
6. §0's =send= signature takes =(token, to, amount)=. The built one takes
   =(evm_nonce, key_version, token, to, amount)=: §7's two values are
   still the caller's, and §3 says so — the README example cannot hide
   them until §7 gives them a home.

** The treasury suite, as a table
=tests/treasury.rs= builds every =ProofPreimage= by hand — the Impact op
stream, the argument slots, the witnesses, and a real secp256k1 signature
over a real Poseidon attestation digest — and runs it through the
simulator, the way =tests/vault_pending= does for the vault. Fifteen
tests; the four rows that matter:

| attestation             | complete | refund (owner) | refund (stranger) |
|-------------------------+----------+----------------+-------------------|
| this kind, flag =true=  | ACCEPT   | reject         | reject            |
| this kind, flag =false= | reject   | ACCEPT         | reject            |
| the MPC's failure kind  | reject   | ACCEPT         | reject            |
| not in the map          | reject   | —              | —                 |

The middle row is what the milestone is about, and it is the row the
deployed vault gets wrong. =anyone_can_complete= pins the completion's
private transcript as EMPTY — there is no secret in the circuit, so a
stranger's proof is the same proof — and
=a_failure_signature_does_not_verify_under_the_executed_kind= is the
negative control for the two-preimage selection: relabelling a failure
attestation's kind byte leaves its signature over the three-element
preimage, and the four-element branch rejects it.
